# アップデート手順

Banto のアップデートは2手順です。どのバージョンからでも最新に上げられます。

1. **コードを最新にする**（GitHub のコピーを Banto に追いつかせる → Cloudflare が自動で再配置）
2. **管理画面の「アップデート」でデータベースの変更を適用する**

管理画面のダッシュボードには、現在のバージョン、GitHub 上の最新リリース、未適用の変更があるかが表示されます。

> 先にバックアップを取ることをおすすめします。Supabase の無料プランには自動バックアップがありません。

## 1. コードを最新にする

**Deploy ボタンで導入した場合**

Deploy ボタンは、あなたの GitHub に Banto の**コピー**（フォークではない、別のリポジトリ）を作り、Cloudflare をそのコピーにつなぎます。
コピーには Banto の更新が自動では届かず、フォークではないので GitHub の「Sync fork」も出ません。
次のどちらかでコピーを追いつかせると、Cloudflare が自動で再配置します（Cloudflare の画面 → Workers & Pages → あなたの Worker → デプロイ で進行を確認できます）。

コピーには Cloudflare が手を入れています: `wrangler.jsonc` の `name` がリポジトリの名前（Worker の名前）になり、`.github/workflows/` の CI が外れています。
`name` が Worker の名前と違うと Cloudflare のビルドが止まるので、下の手順はどちらも `name` だけをあなたのコピーの値に保ちます。
コピーのほかのファイルは Banto の内容で置き換わるので、**コピーを直接編集しないでください**（設定は Cloudflare の「変数とシークレット」と管理画面に置きます）。

*A. GitHub の画面だけで（おすすめ。コマンド不要）*

最初の 1 回だけ、コピーに更新用のワークフローを置きます。

1. GitHub で自分のコピーを開き、**Add file → Create new file** を押します。
2. ファイル名に `.github/workflows/sync-banto.yml` と入れ、下の内容をそのまま貼って **Commit changes** を押します。

```yaml
# Banto（bantojs/banto）の最新の main に、このコピーを追いつかせる。
# wrangler.jsonc の name（Worker の名前）だけはこのコピーの値を保つ。ほかのファイルは Banto の内容で置き換わる。
name: Banto に追いつく
on:
  workflow_dispatch:
  # 毎週自動で追いつかせるなら、次の 2 行の先頭の # を外す（月曜 3:00 UTC）
  # schedule:
  #   - cron: "0 3 * * 1"
permissions:
  contents: write
jobs:
  sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4.4.0
      - name: Banto の内容に置き換える
        run: |
          set -euo pipefail
          name=$(sed -n 's/^  "name": "\([^"]*\)",$/\1/p' wrangler.jsonc | head -n 1)
          test -n "$name"
          keep=$(mktemp)
          cp .github/workflows/sync-banto.yml "$keep"
          git fetch --quiet --depth 1 https://github.com/bantojs/banto.git main
          git rm -r --quiet .
          git checkout FETCH_HEAD -- .
          rm -rf .github/workflows
          mkdir -p .github/workflows
          cp "$keep" .github/workflows/sync-banto.yml
          sed -i "0,/^  \"name\": \"banto\",\$/s//  \"name\": \"$name\",/" wrangler.jsonc
          git add -A
          if git diff --cached --quiet; then echo "すでに最新です"; exit 0; fi
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git commit --quiet -m "chore: Banto $(node -p 'require("./package.json").version') に追いつく"
          git push
```

3. 更新するときは、コピーの **Actions → Banto に追いつく → Run workflow** を押します。
   - 「すでに最新です」と出たら、更新はありません。
   - Actions が無効と出たら、コピーの **Settings → Actions → General** で Actions を許可し、「Workflow permissions」を **Read and write permissions** にします。

自動にする（`schedule` の # を外す）と、Banto の main に入った変更が週に 1 回あなたのショップに届きます。
データベースの変更（次の §2）は自動では当たりませんが、当てるまでのあいだもショップは止まりません（下の「適用するまでのあいだ」）。
MAJOR の更新を自動で受けたくない場合は、手動（Run workflow）のままにしてください。

*B. コマンドで（git を使える人）*

コピーを clone したディレクトリで、上のワークフローの `run:` の中身と同じことをします（最後の `git push` で Cloudflare が再配置します）。

**リポジトリをインポートで導入した場合（フォーク）**

GitHub でフォークを開き、**Sync fork → Update branch** を押します。フォークを編集していなければ衝突しません。

**コマンドで導入した場合**

```bash
git pull
npm install
npm run deploy
```

## 2. データベースの変更を適用する

再配置後に管理画面（`/admin`）を開くと、「未適用のマイグレーションがあります」と出ます。**アップデート** を押し、
セットアップのときと同じく **Supabase のアクセストークン**（Account preferences → Access Tokens で発行）を貼って **適用する** を押します。トークンは保存されません。

変更は1つずつトランザクションで適用され、途中で失敗した場合はその変更だけ取り消されます（それ以前に成功した分は残ります）。
失敗したら、画面のエラーを添えて Issue で報告してください。元に戻したい場合はバックアップから復元します。

開発者は `npx supabase db push` でも適用できます。

### 適用するまでのあいだ（コードだけ新しい）

アップデートは強制しません。コードを更新したあと、データベースの変更をすぐに適用しなくても、**お店（お客様の画面）と今までの機能はそのまま動きます**。
新しい変更が必要な機能だけが、適用するまで出てきません（管理画面には「アップデートを適用すると使えます」の案内と、ダッシュボードの「未適用のマイグレーションがあります」が出ます）。

- 古いデータベースのまま動かせるのは **ひとつ前のマイナー版まで** です（例: v0.2 のコードは v0.1 のデータベースで動く。v0.3 のコードを v0.1 のデータベースで動かすことは保証しません）。マイナー版をまたいで上げるときは、間をあけずに適用してください。
- どのバージョンからでも、適用すれば最新に追いつけます（変更は順に当たります）。

### 変更ごとの注意

**v0.2.0** に含まれるのは 0055〜0061 です（下の 0055 から 0061 まで）。v0.1.0 のデータベースのまま v0.2.0 のコードにしても動きますが、0055（権限の締め直し）・0056（回数の上限）・0057（会員の再認証）はセキュリティの修正なので、コードを更新したらすぐに適用してください。お問い合わせ（0061）のために R2 のバケット `banto-private` が増えます（0061 の項）。

- **0066_headless_order_lookup（注文照会・領収書をヘッドレスで）**: 注文照会の関数（`lookup_order`・`member_order`）の中身を 1 つにまとめ（返す形は同じ）、注文メールの材料（`order_contact`）に「会員の注文か」と注文照会のページを足します。ショップ設定のヘッドレス連携に「注文照会のページ」の欄が出ます（適用するまでは出ません）。注文メールの「ご注文の状況」のリンクに `?banto_order=<注文番号>`（会員の注文なら `&banto_member=1`）が付き、会員はログインしていればその注文がそのまま開きます。注文照会・領収書の API（`/api/shops/:shop/orders/lookup`・`/orders/receipt`・`/members/orders/:number`）は適用する前から使えます。
- **0065_sku_option_axes（SKU を分ける軸）**: ショップ・カテゴリー・商品に「SKU を分ける軸」（カラー × サイズ・型番 × 長さなど）の列と関数が増えます。管理画面のカテゴリーの画面と商品の画面に欄が出ます（適用するまでは出ません）。**既存の商品は「決めていない」のまま**で、SKU の選択肢は今までどおり自由です。カテゴリーで軸を決めて「商品に当てる」を押すと、SKU がそのまま合う商品だけに当たります。お店の商品ページは、SKU の選択肢の項目がそろっている商品なら、軸ごとの選択欄（カラー → サイズ）になります（スクリプトが動かない環境では今の 1 つの選択欄）。
- **0064_inquiry_api_attachments（お問い合わせの添付を AI 用 API で）**: AI 用 API（`/api/v1`）で、お問い合わせの返事にファイルを添付し、お客様の添付を受け取れるようになります（受け取りは `inquiries:read` と `orders:pii`。docs/ai-access.md §8）。適用するまでは、添付つきの返事と受け取りは 409 です。文字だけの返事・管理画面・お客様の画面は何も変わりません。
- **0063_sku_images（SKU ごとの画像）**: 商品の画像に、どの SKU の画像か（カラー・サイズなどの選択肢）を持たせる列と関数が増えます。管理画面の商品の画像の欄に、選択肢を選ぶ欄が出ます（SKU に選択肢がある商品だけ。適用するまでは出ません）。結んだ画像がない商品は、お店の画面も商品フィードも何も変わりません。WooCommerce の取り込みは、適用したあとに取り込むと、バリエーションの画像をそのバリエーションの属性に結びます（取り込み済みの商品は、同じ CSV をもう一度取り込めば結ばれます）。
- **0062_legal_links（法務のページを連携サイトに向ける）**: ショップの行に、外のページを確かめた結果の列（`legal_links_state`）と関数が増えます。管理画面のショップ設定に「法務のページを連携サイトで出す」が出ます（適用するまでは出ません）。設定しない限り、お店の画面は何も変わりません（docs/headless.md「法務のページ」）。
- **0061_mod_inquiries（お問い合わせ）**: 同梱モジュール「お問い合わせ」（既定 OFF、docs/inquiries.md）の表と関数が増えます。組織のメンバーの項目に「お問い合わせ」（`support`）が加わります（適用するまでは選べません）。注文の画面の「この購入者の個人情報を削除（マスク）」（`mask_customer`）が、同じアドレスのお問い合わせの連絡先と本文も消すようになり、お問い合わせのメールがプランの 1 日のメールの上限（0053）に数えられます。AI 用トークンのスコープに `inquiries:read` / `inquiries:write` が加わり（適用するまでは発行できません）、バックアップの書き出しと復元にお問い合わせが入ります。お問い合わせの添付ファイルのために、R2 のバケット `banto-private`（Binding `PRIVATE`）が増えます。`wrangler.jsonc` にあるので次のデプロイで作られます。**カスタムドメインや公開の設定は付けないでください**（docs/inquiries.md「添付ファイル」）。モジュールを ON にしない限り、ほかは何も変わりません。適用するまで、モジュールを ON にしてもお問い合わせの画面は出ません。
- **コードだけの変更（2026-10-25 の監査、マイグレーション不要）**: (1) メールの送信元・宛先はアドレスの形（空白・改行を含まない）だけ受け付け、SMTP の送り手は改行を含む行を送りません。メール通知プラグインの「送信元」に改行や制御文字が入っていた場合は落とされます。(2) hooks の送信先に私設のアドレス（10.x・192.168.x・localhost 等）は登録できません。配信・マニフェストの取得・テスト送信はリダイレクトを追わず、応答の本文を上限まで（64KB / 4KB）しか読みません。(3) 書き出す CSV（注文・会員・送り状・クーポン）で、先頭が `=` `+` `-` `@` の文字列のセルは `'` を前置して文字にします（表計算ソフトで式として評価されないように）。送り状の取り込みで名前の先頭に `'` が出る場合は、その行の値を確かめてください。(4) AI 用 API のエラー文言にデータベースの内部名（制約名・列名）を出しません。
- **0057_member_reauth（会員のアカウントに入る手段の追加）**: 2026-10-25 の監査の対応。会員が **パスワードを決める・変える** と **LINE / Google を連携する** 操作は、ログインしてから 15 分以内だけできます（過ぎていれば、確かめのコードで入り直してから）。パスキーの追加と同じ守りです（盗まれた Cookie から入る手段を足されないため）。どちらも本人にメールで知らせます（メール通知プラグインの送信元が設定されているとき）。ヘッドレスの `POST /api/shops/:shop/members/password` は 15 分を過ぎると `403 reauth` を返すので、連携側はログインし直させてください。運営者の二段階認証を外すときは 6 桁をもう一度入れます。登録・解除は監査ログに残ります。
- **0056_rate_limits_2（回数の上限の締め直し）**: 2026-10-25 の監査の対応。(1) 0 円の注文（全額クーポン・0 円の商品）も「同じ人・同じ IP の未確定の予約」の上限（既定 3 / 20）に、直近 1 時間ぶんだけ数えます。(2) 会員のログインのコードの照合の失敗は「そのチャレンジを出した IP ごと」に数えます（第三者が外した回数で本人のコードが止まらない）。(3) 運営者のログインと会員のパスワードのログインのロックは「同じ IP から同じアドレスへ 15 分に 5 回」が先で、アドレス全体は 15 分に 20 回です（第三者が 5 回外しても本人は別の IP から入れる）。運営者の二段階認証の 6 桁の失敗は、パスワードの失敗とは別に数えます。(4) hooks の配信は 1 回の Cron で、Workers のプランが free なら 12 件、paid なら 50 件まで取り出します（サイトの設定 `workers_plan`）。個人情報のマスキングは配信より先に走ります。
- **0055_security_hardening_2（権限の締め直し）**: 2026-10-25 の監査の対応。適用すると次が変わります。(1) AI 用トークンは、発行者がその項目を失うと該当のスコープ（`orders:pii` を含む）が使えなくなります（発行時だけでなく、使うたびに確かめます）。(2) 組織の owner / admin が、スタッフの発行した AI 用トークンを失効できるようになります。トークンの削除・スコープや期限の書き換え・失効の取り消しはできません（失効したら発行し直す）。(3) 「全員に二段階認証を必須」は組織の owner が二段階認証を済ませた状態でだけ変えられます（直接の更新は拒否）。(4) 商品の独自項目のうち「非公開」のものは、anon キーでデータベースを直接読んでも出なくなります。お店の画面と公開 API は `product_public_get` で読みます（**適用するまでは、非公開の項目の値は anon キーを持つ人に見えます**。原価・仕入先のような値を入れている場合は早めに適用してください）。(5) WordPress のパスワードの取り込みは owner / admin だけになり、既にログインしたことのある会員には書き込みません。(6) 会員のパスキーを全部消す操作は owner / admin だけ。(7) `settings` の項目だけのスタッフは、連携の設定（決済後の戻り先・中継元の IP・外部ログインの client_id）を変えられなくなります（`integrations` が要る）。(8) 注文の発送日時は今の時刻の近くしか書けません。(9) 組織の owner / admin でない人は、組織の外にショップを作れません。
- **0053_plan_mail_limit（1 日のメールの上限）**: プランの上限に `mail_per_day`（会員のログインのコードと組織への招待を、デプロイ全体で 1 日（UTC）にいくつまで）が加わります。**既定は上限なし**で、何も変わりません。ホスティングのように送り手を共有する構成で、送り手の評判を守るためのふたです。入れ方は 0052 と同じ（`select site_settings_set('plan_limits', '{"mail_per_day": 2000}');`）。
- **0052_plan_limits（プランの上限）**: デプロイ全体で持てるショップ・商品・会員・組織のメンバーの数に上限を置けるようになります。**既定は上限なし**で、何も変わりません。上限は管理画面からは入れられず、Supabase の SQL エディタで `select site_settings_set('plan_limits', '{"products": 1000}');` のように入れます（AI 用トークンの誤操作で商品が大量にできるのを止めたいときなど）。今の数と上限は「サイトの設定」に出ます。
- **0051_audit_log（監査ログ）**: 「誰が・いつ・何を変えたか」が DB の中に自動で残るようになります（会員のメールアドレスの変更と削除、注文の状態、組織のメンバーと項目、AI 用トークンの発行と失効、ショップの独自ドメイン・Stripe の接続先・公開）。組織の owner / admin が「組織とメンバー」→「監査ログ」で読めます。メールアドレスそのものは残しません。記録は既定 365 日で消えます（`AUDIT_LOG_KEEP_DAYS`）。運営者の作業はありません。適用するまで画面は案内だけを出します。
- **0035_checkout_status（完了画面で確定と注文番号）**: 決済ページから戻った画面が「確定したか・注文番号」を引けるようになります（同梱テーマの完了画面は確認中なら自動更新し、確定したら注文番号を出す。ヘッドレスは `POST /checkout` の `status_token` と `GET /checkout/status`）。運営者の作業はありません。適用するまでは今までどおりの「受付済み」の表示です。
- **0034_relay_ips_private（中継元の IP を公開しない）**: 0033 で公開の settings（お客様の画面が読む `shop_public_get`）に含めていた中継元の IP の一覧を外します。連携側のサーバーの素の IP なので、CDN の後ろに置いていても直接攻撃できてしまうため。Worker は service_role で読みます。運営者の作業はありません（0033 を当てたのが 2026-10-18 より前なら、念のため連携側のサーバーの IP が漏れた前提で WAF の設定を見直してください）。あわせて `GET /api/v1/relay-check`（接続テスト用）と IPv6 の書き方の正規化。
- **0033_relay_limits（中継元の IP と IP ごとの上限）**: WordPress などのサーバーが Banto を中継する構成で、同じ IP の未確定の予約 20・会員ログインのコード発行 1 時間 30 回がサイト全体の上限に化ける件（外部レビューの指摘 2026-10-18）。適用すると、ショップ設定の「ヘッドレス連携」に中継元の IP と 2 つの上限の欄が出ます。**中継構成の運営者の作業**: 連携側のサーバーの送信元 IP を入れ、連携側で `X-Banto-Client-IP` ヘッダーに購入者の IP を入れる（docs/headless.md「サーバー側で中継するとき」）。ブラウザから直接呼ぶ構成（埋め込みスニペット）と同梱テーマだけの運営では何もしなくてよい。既定値と今までの動きは変わりません。
- **0032_api_checkout_terms（確認画面の文言を AI 用 API で）**: `api_shop_get` / `api_shop_update` が `checkout_terms` を扱います。運営者の作業はありません。適用前の DB に `checkout_terms` を渡すと 409 `migration_required`。

- **0030_admin_sessions（運営者の入口。2026-10-18 のコード監査の段階 3）**: (1) **コードを更新した時点で全員がログアウトします**（管理画面の Cookie を暗号文に変えたため。ログインし直すだけ）。(2) 適用すると、ログアウトで**その人のすべての端末**のログインが切れます（Cookie の期限に関係なく即時）。(3) 管理者ログインは同じメールアドレスで 15 分に 5 回、同じ IP で 20 回失敗すると 15 分間断ります（Supabase には問い合わせません）。(4) 最初の運営者の Supabase Auth ユーザーを消しても、ショップか組織のメンバーが残っていれば、セットアップの運営者登録は再び開きません。**それまでは、最初の運営者の Auth ユーザーを消すと、その人のショップ・商品・注文が連鎖して消えていました**（0030 で外部キーを「空にする」に変更）。運営者を入れ替えるときは、先に「組織とメンバー」で次の owner を招待してから消してください。

- **0028_security_hardening（セキュリティの締め直し。2026-10-18 のコード監査）**: 表の作り直しはありませんが、権限が変わります。(1) お客様の画面（anon）が読める `shops` の列を絞り、`settings` は公開の鍵だけを `shop_public_get` / `shop_public_list` で受け取ります。適用するまで Banto は今までどおり列を読み、適用後は関数に切り替わります（isolate ごとに最大 60 秒ずれる）。**anon キーで `shops.settings` や `stripe_account_id` を直接読んでいた独自の連携は動かなくなります**（公開 API `/api/shops/<slug>` を使ってください）。(2) AI 用トークンのスコープは発行者の項目まで。スタッフが項目以上のスコープで発行していたトークンは、そのスコープだけ `unauthorized` になります（発行し直すか、項目を足す）。返金・キャンセルには発行者の `orders_cancel` が要ります。(3) `orders` を管理画面の JWT で直接更新できる列は `status` / `shipped_at` だけ、遷移は 支払い済み → 発送済み だけ（キャンセル・返金は今までどおり画面のボタン = `cancel_order`）。(4) `customers` のパスワードのハッシュ・世代は運営者にも見えません（バックアップの書き出しにも含まれません）。(5) `shop_payment_options` は決済プラグインの表示に要る設定だけ返します。(6) 管理画面から積める hooks のイベントは `product.updated`（catalog）と `order.shipped`（orders）だけ。

## 3. 手動対応項目

GitHub Releases のリリースノートに「手動対応」の項があれば実施します。例:

- Cloudflare の「変数とシークレット」に項目を追加する
- Stripe の Webhook で購読するイベントを追加する

## バージョニングの約束

- セマンティックバージョニング（MAJOR.MINOR.PATCH）
- MINOR までは後方互換。データベースの破壊的変更は MAJOR でのみ行い、1つ前の MAJOR からの移行ガイドを必ず付けます
- カラムの削除・リネームは2段階（新カラム追加 → 次の MINOR で旧カラム削除）
- データベースの変更は「足すだけ」にします（表・列・関数の追加）。コードは、ひとつ前のマイナー版のデータベースのままでも動くように書きます（上の「適用するまでのあいだ」）
- v0.2.0 は 0001〜0054 を土台にします（v0.1.0 のセットアップで全部適用されています）。v0.1.0 のときにアップデート画面で 0054 まで当てていなかった（v0.1.0 より前の開発版から上げてきた）データベースは、v0.2.0 にする前に v0.1.0 のコードのまま最新まで適用してください
- MAJOR の更新では自動更新を促しません。リリースノートの移行ガイドを読んでから判断してください

## うまくいかないとき

| 症状 | 確認すること |
| --- | --- |
| 再配置後に管理画面が開かない | 新しい変数・シークレットが未設定。`/admin/setup` を開くと不足が一覧されます |
| 「未適用のマイグレーションがあります」が消えない | アップデート画面で適用したか。エラーが出た場合はその内容を確認 |
| 追いつかせたあと Cloudflare のビルドが止まる | ログに Worker の名前が違うと出ていれば、`wrangler.jsonc` の `name` が Worker の名前と違います。コピーの `name` を Worker の名前に直します |
| 「Banto に追いつく」が `git push` で失敗する | コピーの Settings → Actions → General の「Workflow permissions」を Read and write permissions にします |
| 「Banto に追いつく」が `workflow` の権限が無いと言って止まる | コピーに `sync-banto.yml` 以外のワークフローがあると、それを消す push が断られます。GitHub の画面でそのファイルを消してから、もう一度 Run workflow を押します |
| Sync fork に「This branch is out-of-date」以外の表示（フォーク） | フォークを直接編集していると衝突します。編集していなければ Update branch で進めます |
