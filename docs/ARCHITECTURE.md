# Banto Architecture & Design Document

Oct 14, 2026 · @角田

## 本書の位置づけ

本書は「EC SaaS Architecture & Design Document」を、SaaSではなくOSS（セルフホスト型）として配布する前提で書き直したものです。中小企業・個人事業主が自分のCloudflareアカウントとSupabaseプロジェクト上にデプロイして使う、軽量・拡張型のECプラットフォームを定義します。

基本思想はSaaS版から変えません。決済・CRMなど法的リスクを伴う領域は自前で持たず、利用者自身の外部アカウントに連携させる（Composable Commerce / BYOKey）。OSS版ではこれをインフラにまで広げ、DB・ストレージ・実行環境も利用者自身のアカウントで動かします（BYO Infrastructure）。開発チーム側はコードとドキュメントだけを提供し、資金・個人情報・稼働責任を一切持ちません。

対象読者は、本プロジェクトの開発メンバー、およびセルフホストして運用するショップ運営者（技術担当）です。

## 配布形態とライセンス

本プロジェクトの名称は Banto（番頭）とし、MITライセンスのOSSとして GitHub（org: bantojs）で公開します。利用者が自身のアカウントにセルフホストする形で提供し、開発チームはホスティングを行いません。名称は江戸の商家で店を切り盛りした「番頭」に由来し、運営者に代わって注文・在庫・決済連携を回す本システムの役割を表します。公式サイトは bantojs.dev、npm パッケージ名および CLI 名は banto です。

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| ライセンス | MIT | 商用利用者の法務審査を通りやすい。第三者がホスティング提供することは歓迎（有志チームの運用負担を肩代わりしてもらえる）。Hono・Supabase周辺のMIT/Apacheエコシステムと相性がよい |
| 配布単位 | 1デプロイ＝1運営者 | 1人（1法人）のCloudflare + Supabaseアカウントに1インスタンス。他人同士の同居を前提にしない |
| ショップ数 | 1運営者につき複数可 | 同一運営者が複数ブランド・複数店舗を持つ需要に対応。shop\_idで分離 |
| 保証 | 無保証（AS IS） | LICENSE本文とREADME冒頭に明記。稼働・データ保全・法令適合の責任は運営者にある |
| 費用 | 開発チーム側は0円 | インフラ費は利用者負担。小規模ならCloudflare・Supabaseの無料枠で収まる想定（容量・停止ポリシーは各社の最新規約に従う） |

AGPL-3.0への切り替えは、開発チーム自身が有料ホスティングを事業化する判断をした時点で再検討します。それまで守るべき商売がないため、採用障壁の低いMITを選びます。

## コア技術スタック

技術スタックはSaaS版から変更しません。変わるのは「誰のアカウントで動くか」だけで、すべて運営者自身のCloudflare / Supabaseアカウント上で稼働します。

| レイヤー | 採用技術 | 選定理由 | OSS版での補足 |
| --- | --- | --- | --- |
| API / サーバー | Cloudflare Workers + Hono | エッジ実行で低レイテンシ、TypeScript対応が良い | wrangler.jsonc を同梱し、Deploy ボタンから1クリックで配置 |
| データベース | Supabase (PostgreSQL) | RLS、Auth、Storage、RPCが揃っている | supabase/migrations をリポジトリに同梱。運営者が自分のプロジェクトに適用 |
| メディアストレージ | Cloudflare R2 | エグレス無料、画像大量配信に向く | 運営者のアカウントにバケット作成。Workers Binding で接続し、キーを環境変数に置かない |
| ストアフロント | Hono SSR（初期）＋ ヘッドレスAPI | 初期はSSRで速く出し、後から外部フロントへ拡張 | Next.js 等の外部フロントはヘッドレスAPI経由。テーマはリポジトリ内で差し替え可能にする |
| 管理画面 | Hono SSR | 運営者用。別Workerに分けない | 初回アクセス時のセットアップウィザードもここに含む |

依存は上記5つに絞ります。メール送信・検索・分析など追加機能は、コアに取り込まず外部サービス連携（次節）かプラグインとして扱います。

## ポータビリティ方針

Cloudflare Workers から別の実行環境へ移る事態に備え、Cloudflare 固有の機能はアダプタ層の背後に隔離し、KV と Durable Objects は使いません。Hono はマルチランタイム（Node.js、Bun、Deno、Vercel、AWS Lambda 等）で動くため、API と SSR の本体はそのまま持ち出せます。Supabase は標準の PostgreSQL であり、pg\_dump で他の Postgres へ移行できます。

**5つのアダプタ**

| アダプタ | Workers 実装（既定） | 脱出先の実装 | 備考 |
| --- | --- | --- | --- |
| StorageAdapter | R2 Binding | S3 互換 API（AWS S3、Backblaze B2、MinIO。R2 自身も S3 API で接続可） | 画像 URL は CDN ドメインを環境変数化し、保存先を変えてもリンクを切らない。R2 を離れると転送量課金が発生するため、脱出は最後の手段 |
| ConfigAdapter | Workers 環境変数 / Secret | プロセス環境変数、`.env` | 秘密情報の取得経路を一箇所にまとめる |
| SchedulerAdapter | Cron Trigger | node-cron、または Postgres の pg\_cron | 在庫予約の期限解放など定期処理に使用 |
| CacheAdapter | Cache API（標準 Web API）+ isolate 内メモリ | 同じ Cache API、またはメモリキャッシュ | KV の代替。公開ページの商品一覧・詳細を数十秒〜数分キャッシュし、Supabase への往復を減らす |
| SocketAdapter | `cloudflare:sockets`（生の TCP） | `node:net` / `node:tls` | SMTP でメールを送るためだけ。HTTP の送り手（Resend / SendGrid / SES）は fetch なので要らない |

**使わないもの**

| 機能 | 使わない理由 | 代替 |
| --- | --- | --- |
| Workers KV | 固有機能。設定キャッシュ用途は Cache API で足りる | Cache API + メモリキャッシュ |
| Durable Objects | 固有機能。在庫や カートの一点制御に便利だが、この規模では Postgres で十分 | 在庫は条件付き UPDATE の RPC、カートは Supabase テーブルまたは署名付き Cookie |
| Hyperdrive | 固有の接続プーラー | Workers から直接 Postgres 接続を張らず、Supabase REST API（PostgREST）経由で叩く。無料プランの接続数上限も回避できる |
| レート制限の自前実装 | DO が必要になる | Cloudflare WAF のレート制限ルールで対応。アプリコードに依存させない |

**失うものと得るもの**

KV と Durable Objects を封印することで、エッジで完結する速さ（Supabase 往復分の 50〜150 ms）と、限定販売のような超高負荷への耐性を失います。個人・中小規模の EC ではどちらも問題にならず、代わりにどの環境へも移せる自由を得ます。ホスティング版を検討する時点で、在庫処理への Durable Objects 採用を再評価します。

**運用ルール**

- CI では Workers 向けと Node.js 向けの両方をビルドしてテストし、気づかないうちに Cloudflare 専用になることを防ぐ
- `docs/run-on-node.md` に Node.js + Docker で動かす手順を置き、脱出経路を常に検証可能にしておく
- Supabase Auth は移行時に書き直しになるため、owner 認証はメール + パスワードの最小構成に留め、依存を広げない

## テナントモデル

1デプロイに運営者（owner）が1人おり、その配下に複数のショップがぶら下がります。見知らぬ他人同士が同じDBに同居することは想定しません。

**階層**

1. owner：Supabase Auth のユーザー。デプロイごとに1人（将来、同一組織内の複数スタッフをmember として追加できる余地を残す）
2. shop：owner に属する店舗。独自ドメイン・テーマ・決済連携・CRM連携をそれぞれ持つ
3. 商品・注文・顧客・在庫：すべて shop\_id を持ち、ショップ単位で分離

**RLSの適用方針**

SaaS版の「RLSでテナント隔離」は、Workers側で service\_role キーを使うと素通りになります。OSS版では次の方針で、RLSが実際に効く経路だけを使います。

| 経路 | 使うキー | RLS | 用途 |
| --- | --- | --- | --- |
| 管理画面（owner操作） | ユーザーJWT（anon キー + Auth セッション） | 効く。`auth.uid()` が owner と一致し、かつ対象行の shop が owner に属する行のみ許可 | 商品登録、注文確認、設定変更 |
| ストアフロント（匿名閲覧） | anon キー、セッションなし | 効く。`published = true` の商品・ショップ情報のみ SELECT 許可 | 商品一覧、商品詳細 |
| 注文確定・在庫減算・Webhook受信 | service\_role キー（Workers Secret） | 効かない。RPC関数内で shop\_id を必ず引数に取り、関数内で検証 | チェックアウト、決済Webhook、在庫RPC |

service\_role を使う処理は専用モジュールに閉じ込め、通常のCRUDからは呼べないようにします。これにより「RLSで守っているつもり」の事故を構造的に防ぎます。

1運営者＝1デプロイにしたことで、他運営者とのデータ混在リスクがそもそも存在しません。RLSの役割は「ショップ間の整理」と「公開/非公開の制御」に限定され、SaaS版より大幅に単純になります。

## 外部サービス連携

資金と顧客データの主体は運営者自身の外部アカウントに置き、本システムは接続役に徹します。セルフホストなので鍵は運営者自身の環境にしか存在しませんが、それでも「秘密鍵をDBに保存する」設計は避けます。

| 機能領域 | 連携方式 | SaaS版からの変更点 |
| --- | --- | --- |
| 決済（Stripe） | Stripe Connect Standard（OAuth）。運営者が自分のStripeアカウントを接続し、本システムは接続済みアカウントIDだけを保持 | シークレットキーの預かりを廃止。鍵漏洩時の被害範囲をゼロにする |
| 決済（KOMOJU） | 現時点ではAPIキー方式。Workers Secret に保存し、DBには置かない | 同上。OAuth相当の仕組みが提供されれば移行 |
| クレジットカード情報 | Stripe Checkout / KOMOJU ホスト型決済ページへリダイレクト | カード番号は一切通過させない（PCI DSS SAQ A 相当） |
| CRM / MA | HubSpot、Klaviyo、LINE 等へ注文・顧客イベントをWebhookで送信。APIキーは Workers Secret | 変更なし。送信先の増減はプラグイン形式で |
| メール送信 | 運営者の Resend / SendGrid / Amazon SES、または運営者自身の SMTP サーバー（`MAIL_TRANSPORT` で 1 つ選ぶ。docs/email.md）。注文確認メールを CRM 側に委ねる選択肢も残す | 当初は「コアに SMTP 実装を持たない」としていたが、レンタルサーバー・VPS の利用者が自分のメールサーバーを使えるように、ライブラリなしの小さな SMTP クライアントを入れた（人間の決定 2026-10-23）。接続は SocketAdapter の背後 |
| ストアフロント | ヘッドレスAPI（公開読み取り + 署名付きカートAPI） | 変更なし。Next.js 等の外部フロントを接続可能 |

**Webhookの受信**

決済完了は必ずWebhookで確定し、フロントのリダイレクト完了をもって注文確定としません。Webhook署名の検証と冪等性キー（イベントID）の保存をコアに実装し、二重処理を防ぎます。

**プラグイン境界**

CRM・メール・分析はコアの `hooks`（order.created、order.paid、customer.created など）を購読する形で実装し、サードパーティが連携先を追加できるようにします。コア本体は連携先の仕様を知りません。

## プラグインアーキテクチャ

**3 層に分ける（2026-10-16 決定、docs/knowledge/02-decisions.md）**

コアを膨らませないために、機能を次の 3 層のどれかに置きます。WordPress のように第三者のコードを稼働中に読み込む方式は採りません（Cloudflare Workers はコード全体を 1 バンドルとしてデプロイするため）。

| 層 | 中身 | 付け外し | 例 |
| --- | --- | --- | --- |
| コア | **データの器**（汎用の部品）と**判定の一本道**（価格・値引き・送料・税・在庫・注文確定・特商法の表示）。個別の機能は持たない | 常に有効 | 商品・SKU・カテゴリー・カスタム項目の器、quote と確定、拡張点 |
| 同梱モジュール | 開発チームが書いてレビューし、本体に同梱する機能。コアの**拡張点**だけを実装する | 管理画面のトグル。**既定は OFF**。再デプロイ不要 | クーポン、商品フィード（Google / Meta）、WooCommerce インポーター、送り状 CSV、配送日時指定、LINE 通知・メール・KOMOJU（hooks の受け手として同梱するもの） |
| 外部プラグイン | 別の Worker または任意のサーバー。コアとは hooks（署名付き Webhook）とヘッドレス API で通信 | 管理画面で URL を登録 | CRM、レビュー、Meta / Google への API 即時同期、第三者製のもの |

**どこに置くかの判定基準**

1. お金・在庫・法務の正しさに関わる → 判定はコア。機能そのものは同梱モジュールにし、コアの拡張点を経由させる
2. データの形が必要 → コアは「汎用の器」だけを持つ（例: カスタム項目は jsonb と項目定義）
3. 使わない人が多い → 既定 OFF の同梱モジュール
4. 外部サービスの仕様に依存する → 同梱モジュールか外部プラグイン（相手の仕様変更でコアが壊れない）
5. 後から非同期で動けばよい → 外部プラグイン（hooks）

**拡張点（コアが用意する口）**

| 拡張点 | 内容 | 実装するモジュールの例 |
| --- | --- | --- |
| hooks の受け手 | イベントを非同期で受ける（既存） | メール、LINE 通知 |
| 決済 | 決済ページの作成と Webhook 受信（既存） | Stripe、KOMOJU |
| 値引き | quote に調整行（値引き・手数料）を足す。確認画面の表示と確定時の照合はコアが行う | クーポン |
| 配送 | 送料と配送の選択肢（国を受け取れる形）。今の「全国一律 / 都道府県別」は標準実装 | 配送日時指定、店頭受け取り、将来の海外配送 |
| 読み取り出力 | 公開データを別の形式で出す URL（Cron で生成して StorageAdapter に置く） | 商品フィード、構造化データ |
| 管理画面の取り込み・書き出し | ブラウザ側で処理し、Worker には小分けのデータだけ送る | WooCommerce インポーター、送り状 CSV |
| お店の画面の `<head>` | ON のショップのお店の画面（管理画面を除く）に、決まった形のタグ（https の外部スクリプト・モジュールのコードが作るインラインのスクリプト）を入れる。コアはお店の画面で起きた出来事（商品を見た・カートに入れた・購入した など）を中立の形で渡すだけで、分析サービスの仕様は知らない（`src/storefront/head.ts`・`events.ts`）。運営者が入力した HTML をそのまま出す口は作らない | Google アナリティクス（GA4） |

**同梱モジュールの約束**

- 既定 OFF。OFF のときはルート・メニュー・計算のどれも通らない
- ON/OFF はショップ設定（キャッシュ済みのショップ行）で判定し、そのために DB へ問い合わせない
- コアの内部を直接触らず、拡張点のインターフェースだけを使う
- マイグレーションはファイル名でモジュールを示す（例: `0010_mod_coupons.sql`）。テーブルは全環境に作られ、OFF なら空のまま。RLS などの規約はコアと同じ
- コアに何かを足すときは、判定基準のどれに当たるかを docs/knowledge/02-decisions.md に書く

**速度の予算（「ヘッドレス・高速・軽量」を守る）**

WooCommerce が遅くなる主因は、プラグインが毎リクエスト読み込まれて処理を差し込むことです。Banto はこれを構造的に禁止し、数字で検査します。

- モジュールは拡張点が呼ばれたときだけ動く。拡張点は使われたときだけ DB に問い合わせる（例: クーポンはコードが入力されたときだけ照会）
- 主要ページの DB 往復回数を CI のテストで固定する（`test/perf-budget.test.ts`）。増やすときは理由を書いて数字を変える
- Worker 本体の圧縮後サイズに上限を置き、CI で検査する（`npm run check:size`、上限 1 MiB。Workers 無料プランの上限は 3 MB）
- Workers 無料プランの CPU 制限（1 リクエスト 10 ms）を超える処理をリクエスト中にしない。重い処理はブラウザ側（管理画面）か Cron で行う
- 一覧の絞り込みはキャッシュ済みの全件をメモリで行う（数千件規模までの前提）。超えたら DB 側の絞り込みに移す

**依存ライブラリの基準（禁止ではなく基準と予算）**

1. まず標準機能（`fetch`、`crypto`、`Intl`、ストリーム等、Workers と Node の両方にあるもの）を使う
2. 重い処理はブラウザ側（管理画面のそのページだけ）でライブラリを使ってよい。Worker のサイズと CPU 制限に影響しない
3. Worker 側に入れる条件: Workers と Node の両方で動く、ネイティブ依存が無い、Cloudflare 専用でない、テレメトリを送らない。追加するサイズを PR に書く
4. セキュリティや正確さに関わる処理（暗号、文字コード変換、PDF 等）は無理に自作しない
5. サイズの上限を超えるときは、理由を 02-decisions.md に書いて上限を上げる

**外部プラグインの動かし方**

開発チームはプラグインをホストしません。公式の外部プラグインはコア本体と同じく「Deploy to Cloudflare」ボタン付きリポジトリとして配布し、運営者が自分のアカウントに Worker を追加で立てます（BYO Infrastructure と同じ原則）。第三者作者が自分でホストして URL を公開する形も同じ仕組みで動き、その場合の責任は作者と運営者の間で完結します。コアは「誰がホストしているか」を知りません。

**コアが公開する接点**

| 接点 | 内容 |
| --- | --- |
| hooks（Webhook送信） | `order.created` / `order.paid` / `order.shipped` / `order.cancelled` / `customer.created` / `customer.updated` / `customer.deleted` / `product.updated` / `inventory.low`。署名付き POST。失敗時は指数バックオフで最大5回再送 |
| ヘッドレスAPI | 商品・注文・顧客の読み書き。プラグインごとにスコープ付き API トークンを発行し、管理画面で権限を確認できる |
| 管理画面の拡張 | プラグインが返すマニフェスト（JSON）で設定項目を宣言し、コアがフォームを描画する。独自画面が必要な場合は iframe 埋め込み |
| ストアフロントの拡張 | テーマテンプレート内の拡張スロット（カート下、商品詳細下など）に、プラグインが HTML 断片を返す |

**テーマ**

テーマは SSR テンプレートディレクトリの差し替えで対応し、こちらは再デプロイ前提です。管理画面から切り替えられるのは同梱テーマ間の選択までとします。

**採らない方式**

Workers for Platforms によるサンドボックス実行（運営者がコードをアップロードして動かす方式）は、有料かつ運用が重いため OSS 版では採用しません。ホスティング版を検討する際に再評価します。

## 導入体験（セットアップ）

非エンジニアの個人事業主でも、READMEを読まずに30分以内で最初のショップを公開できることを目標にします。導入の摩擦はOSS版の採用率を直接決めるため、コア機能と同じ優先度で設計します。

**導入の流れ**

1. 運営者が Supabase で新規プロジェクトを作成する（Project URL、anon キー、service\_role キーを控える）
2. README の「Deploy to Cloudflare」ボタンを押す。GitHub リポジトリの fork と Workers へのデプロイが自動で走る
3. デプロイ完了後の URL にアクセスすると、セットアップウィザードが起動する
4. ウィザードで Supabase の URL とキーを入力。本システムが接続確認とマイグレーション適用を行う
5. owner アカウント（メールアドレス + パスワード）を作成する
6. 最初のショップ名を入力し、Stripe Connect の接続画面へ進む（後回し可）
7. ダッシュボードが開き、商品登録ができる状態になる

**リポジトリに同梱するもの**

| ファイル / ディレクトリ | 役割 |
| --- | --- |
| `wrangler.jsonc` | Workers 設定。R2 バケットの Binding、環境変数名の定義 |
| `supabase/migrations/` | DBスキーマ、RLSポリシー、RPC関数。Supabase CLI 形式 |
| `supabase/seed.sql` | デモ用の商品データ（任意で投入） |
| `.dev.vars.example` / `docs/env.md` | Secret の雛形（Deploy ボタンが読む）と環境変数の一覧 |
| `docs/setup.md` | ボタンを使わない手動セットアップ手順（wrangler CLI 経由） |
| `docs/upgrade.md` | アップデート手順（後述） |

**環境変数**

| 変数名 | 置き場所 | 内容 |
| --- | --- | --- |
| `SUPABASE_URL` | Workers 環境変数 | Supabase プロジェクト URL |
| `SUPABASE_ANON_KEY` | Workers 環境変数 | 公開可能キー。ストアフロントと管理画面が使う |
| `SUPABASE_SERVICE_ROLE_KEY` | Workers Secret | 注文確定・Webhook・在庫RPC 専用 |
| `STRIPE_CLIENT_ID` / `STRIPE_SECRET_KEY` | Workers Secret | Stripe Connect の OAuth 用（運営者自身のプラットフォームアカウント） |
| `STRIPE_WEBHOOK_SECRET` | Workers Secret | Webhook 署名検証 |
| `SESSION_SECRET` | Workers Secret | 管理画面セッションの署名。ウィザードが自動生成 |
| `MEDIA` | wrangler.jsonc の Binding | 商品画像バケット。キーは不要 |

**将来のインストーラー構想（v0.2 以降）**

非エンジニアの導入障壁は「アカウントを2つ作り、キーを控えて貼る」工程にあります。これを、ホストしない前提のまま解消するため、ステートレスなインストーラーを別途提供します。

| 項目 | 内容 |
| --- | --- |
| 形態 | GitHub Pages に置く静的な1ページ。開発チーム側にサーバーもDBも持たない |
| 認証 | Cloudflare と Supabase への OAuth / API トークンで、利用者自身のアカウントに一時的な権限をもらう |
| 処理 | 利用者のブラウザ内で、Supabase プロジェクト作成 → マイグレーション適用 → Worker デプロイ → Secret 設定 → owner 作成までを自動実行 |
| 完了後 | ショップ URL を表示して終了。トークン・キーは保存せず、インストーラーはそれ以降関与しない |
| 責任範囲 | 配管工事の代行のみ。データ・稼働・法令対応は引き続き運営者側 |

残る壁は Cloudflare / Supabase のサインアップ2回で、ここは動画付きの日本語ガイドと「クレジットカード登録なしの無料枠で開始できる」旨の明記で埋めます。

**導入パートナー**

自力導入が難しい運営者向けに、README に有償で導入を請け負う制作会社・フリーランスの一覧を置きます。開発チームは紹介のみで、契約や保証には関与しません。MIT ライセンスのため、第三者がホスティング版を提供することも妨げず、「運営は第三者、ソースは本プロジェクト」という分業を歓迎します。

## データと個人情報

注文には配送先の氏名・住所・電話番号・メールアドレスが含まれるため、「個人情報を保持しない」設計は成立しません。OSS版では「個人情報を保持するのは運営者自身のSupabaseであり、開発チームは一切触れない」と定義し直します。個人情報保護法上の取扱事業者は運営者です。

**保持最小化の方針**

| データ | 扱い |
| --- | --- |
| クレジットカード情報 | 一切保持しない。ホスト型決済ページで完結 |
| 配送先・連絡先 | 注文テーブルに保持。発送完了から一定期間（既定180日、運営者が変更可）経過後に自動マスキングするRPCを同梱 |
| 顧客アカウント | 既定ではゲスト購入のみ。会員機能はSupabase Authを使い、運営者が有効化 |
| CRM連携 | 注文・顧客イベントをWebhookで即時転送。CRM側を正とし、本システム側は運用に必要な最小項目だけ残す運用を推奨 |
| アクセスログ | Cloudflare 側に依存。コアでIPアドレスを保存しない |

**運営者の責務（READMEとdocsに明記）**

- プライバシーポリシーの作成と掲載
- Supabase プロジェクトのバックアップ設定（無料プランは自動バックアップなし）
- 退会・削除依頼への対応。管理画面に顧客単位の削除機能を用意する
- 海外リージョンの Supabase を使う場合の越境移転に関する説明

**開発チーム側の立場**

開発チームはどのデプロイのデータにもアクセスできず、テレメトリも送信しません。利用統計が必要になった場合は、運営者が明示的にオプトインする方式のみ検討します。

## 在庫競合制御

同時購入によるオーバーセルは、Workers側ではなくPostgreSQL内の単一RPCで防ぎます。Workersはステートレスで複数インスタンスが並走するため、アプリ層でのロックは成立しません。

**基本設計**

1. チェックアウト開始時に `reserve_stock(shop_id, items[], reservation_ttl)` を呼ぶ。関数内で対象SKUを `UPDATE ... SET available = available - qty WHERE available >= qty` により原子的に減算し、1行でも失敗したらトランザクション全体をロールバックして在庫不足を返す
2. 決済セッションを作成し、予約IDを決済メタデータに紐づける
3. 決済Webhook受信時に `confirm_reservation(reservation_id)` で予約を確定注文に変換する
4. TTL（既定15分）を過ぎた未確定予約は、Workers Cron Trigger から `release_expired_reservations()` を呼んで在庫に戻す

**設計上のポイント**

- 減算は `SELECT ... FOR UPDATE` ではなく条件付きUPDATEで行い、ロック待ちを最小化する
- RPCはすべて `SECURITY DEFINER` で定義し、service\_role 経由でのみ呼べるようにする。shop\_id は引数で受け取り、関数内で SKU の所属を検証する
- 在庫の正は `inventory` テーブルの1行のみ。商品テーブル側に在庫数を複製しない
- Webhookの再送に備え、`confirm_reservation` は同じ reservation\_id に対して冪等にする

複数倉庫や予約販売（在庫マイナス許容）はコアに含めず、`inventory` テーブルの拡張ポイントだけ残します。

## アップデートとバージョン管理

セルフホスト環境のアップデートは「fork を upstream に追従 → 再デプロイ → マイグレーション適用」の3手順に固定し、どのバージョンからでも最新に上げられることを保証します。

**バージョニング**

- セマンティックバージョニング（MAJOR.MINOR.PATCH）。GitHub Releases にリリースノートを付ける
- MINOR までは後方互換を保つ。DBスキーマの破壊的変更は MAJOR でのみ行い、1つ前の MAJOR からの移行パスを必ず用意する
- 管理画面のダッシュボードに現在のバージョンと最新リリースの差分を表示する（GitHub Releases API を参照。取得失敗時は表示しないだけで動作に影響させない）

**マイグレーションの方針**

| 方針 | 内容 |
| --- | --- |
| 前方専用 | ロールバック用マイグレーションは書かない。失敗時はバックアップから復元する手順を docs に用意 |
| 追加優先 | カラム削除・リネームは2段階（新カラム追加 → 次のMINORで旧カラム削除）で行う |
| 適用主体 | 初回はウィザードが適用。以後は管理画面の「アップデート」ボタンから `supabase_migrations` テーブルを見て未適用分だけ実行 |
| 事前チェック | 適用前に Supabase の接続とバックアップ有無（Pro以上か）を確認し、無料プランには警告を出す |

**アップデート手順（docs/upgrade.md に記載）**

1. GitHub 上で fork の「Sync fork」を実行する（Deploy ボタン利用者は Cloudflare が自動で再ビルド）
2. 再デプロイ完了後、管理画面にアクセスすると未適用マイグレーションの通知が出る
3. 「アップデートを適用」を押す。適用中はストアフロントをメンテナンス表示にする
4. 完了後、リリースノートの手動対応項目（環境変数の追加など）があれば実施する

大きな変更（MAJOR）では自動更新を促さず、リリースノートに移行ガイドを添えて運営者の判断に委ねます。

## 法務・運営体制

OSS化により、SaaS版で最も重かった「プラットフォーム運営者としての法的責任」はほぼ消えます。残るのは、運営者が法令を守りやすくするための仕組みと、OSSプロジェクトとしての最低限の体制です。

**SaaS版から消える項目**

| 項目 | 理由 |
| --- | --- |
| 管理者用キルスイッチ | 不正ショップは運営者自身のデプロイであり、開発チームに停止権限も義務もない |
| プラットフォーム利用規約 | ホスティングしないため不要。LICENSE（MIT）と README の無保証表記に置き換える |
| 資金決済法・PCI DSS 対応 | 資金もカード情報も開発チームを通らない。運営者と決済事業者の間で完結 |
| 不正通報の受付窓口 | 開発チームには対応権限がない。通報は決済事業者・ドメイン事業者・警察へ案内する文面を docs に置く |

**残る項目**

- 特定商取引法に基づく表記：ショップ設定にテンプレート入力欄を設け、必須項目が未入力のあいだはショップを公開できないようにする
- プライバシーポリシー・返品ポリシー：同様にテンプレートと公開前チェック
- 無保証と責任制限：LICENSE 本文に加え、README 冒頭と管理画面のフッターにも明記する
- 脆弱性報告：`SECURITY.md` を置き、報告窓口（GitHub の非公開の脆弱性報告。リポジトリ側で有効にする）と対応目標（受領48時間以内に返信）を記載する
- 行動規範：`CODE_OF_CONDUCT.md`（Contributor Covenant）

**有志チームの運営**

- 意思決定：GitHub Discussions で公開議論し、メンテナ2名以上の承認でマージ
- バス係数：メンテナ権限は常に2名以上。Cloudflare / Supabase のデモ環境アカウントは共有パスワードマネージャで管理
- プロジェクト終了時：リポジトリをアーカイブすれば済む。既存デプロイは運営者の手元で動き続けるため、移行対応は不要（これがOSS化の最大の利点）

## MVP開発ステップ

SaaS版の4ステップを、OSS版では「他人に渡せる状態」を各段階で満たすよう並べ直します。在庫RPCと公開前チェックを決済連携より前に置くのが変更点です。

1. リポジトリ初期化：MIT LICENSE、README（無保証表記）、SECURITY.md、CODE\_OF\_CONDUCT.md、wrangler.jsonc、`.dev.vars.example`
2. Supabase スキーマ：owner / shop / product / sku / inventory / order / reservation のマイグレーションと RLS ポリシー。在庫RPC（reserve / confirm / release）をここで実装しテストする
3. セットアップウィザードと Deploy ボタン：Supabase 接続、マイグレーション自動適用、owner 作成、最初のショップ作成。Secret の受け渡し方式をここで決定する
4. 商品管理と R2 画像アップロード：管理画面からの登録、Binding 経由のアップロード、公開/非公開の切り替え
5. Hono SSR ストアフロント：商品一覧・詳細・カート。特商法表記などの公開前チェックをここで有効化する
6. Stripe Connect 決済：OAuth 接続、Checkout セッション作成、Webhook による注文確定、予約在庫の確定と解放
7. アップデート機構：バージョン表示、未適用マイグレーションの検出と適用
8. 公開：v0.1.0 としてリリース。docs/setup.md と docs/upgrade.md を揃え、第三者が README だけで導入できることを確認してから公開する

ステップ 3 までを完了した時点で、開発メンバー以外の1人に実際にセットアップさせるテストを行います。ここで詰まる箇所が、OSS版の実質的な最重要課題になります。

## 将来拡張：ホスティング版の可能性

OSS版が安定した後、同じコードベースで有料のマネージド版を提供する道は残しておきます。ただし現時点では着手せず、以下の条件が揃った時にのみ判断します。

**ホスティング版を検討する条件**

- セルフホスト導入者が一定数（目安100デプロイ）を超え、「自分でホストしたくない」という要望が繰り返し出ている
- 月額インフラ費とサポート対応を賄う運営主体（法人または明確な責任者）が存在する
- メンテナが2名以上、継続的に稼働している

**その時に変わるもの**

| 項目 | OSS版 | ホスティング版 |
| --- | --- | --- |
| ライセンス | MIT | AGPL-3.0 への変更を検討（既存リリースはMITのまま） |
| テナント | 1デプロイ＝1運営者 | 1プロジェクトに複数運営者。RLSをテナント隔離の主役に戻す |
| 個人情報 | 運営者が取扱事業者 | 運営主体も取扱事業者になる。プライバシーポリシーと利用規約が必要 |
| 不正対策 | 不要 | キルスイッチ・通報窓口・審査が必要 |
| 収益 | なし | 月額課金または決済手数料の上乗せ |

**コード上で今から守ること**

- owner を単一前提でハードコードせず、常に `owner_id` を持たせる。これだけで将来のマルチテナント化の工数が大きく変わる
- インフラ固有の処理（R2、Workers Secret）は抽象化層を1枚挟み、他環境へ移せる余地を残す
- 設定値は DB ではなく環境変数に寄せすぎない。ホスティング版ではショップごとに DB 側で持つ必要がある

いずれにせよ、OSS版の設計を先に固めることが、ホスティング版への最短経路になります。順番を逆にしないこと。

**ホスティング版のDB方針**

ホスティング版では、共有DBを owner\_id で分離するプール型を既定とし、大口の運営者だけを専用プロジェクト（サイロ型）へ切り出せる設計にします。

| 方式 | 内容 | 費用 | 隔離 | 運用 |
| --- | --- | --- | --- | --- |
| プール型（既定） | 1つの Supabase プロジェクトに全運営者。全テーブルに owner\_id、RLS で隔離 | 最安。Pro 1本から開始 | 論理隔離。RLS の書き漏れが事故になる | マイグレーション1回、バックアップ1本 |
| スキーマ型 | 運営者ごとに Postgres スキーマ | プール型と同じ | 中間 | マイグレーションを運営者数ぶん実行。数百を超えると PostgREST が重くなるため採用しない |
| サイロ型（大口向け） | 運営者ごとに Supabase プロジェクト | 運営者1人につき月額固定費 | 物理隔離 | OSS 版のセルフホストと同じ。デプロイ代行に相当 |

プール型で必要になる実装：

- JWT に owner\_id をカスタムクレームとして持たせ、RLS と RPC 内の両方で検証する二重チェック
- 全テーブルの RLS 有効化を CI で検査し、RLS のないテーブルを存在させない
- owner\_id（または shop\_id）を先頭にした複合インデックス。注文・在庫履歴など肥大化するテーブルは owner\_id でパーティション
- 接続は Supavisor と PostgREST 経由で吸収し、Workers から直接 Postgres 接続を張らない
- 運営者単位のエクスポート RPC。大口のサイロ化、退会時のデータ返却、セルフホストへの移行を同じ仕組みで扱う

プール型の弱点は2つあります。1つは特定運営者のセールで全員が遅くなる「うるさい隣人」問題で、コンピュートの増強かサイロ化で対処します。もう1つは運営者単位のバックアップ復元ができないことで、エクスポート RPC を日次で実行して R2 に保管する運営者別バックアップを自前で持ちます。

プール型でも Pro の月額と運営者増加に伴うコンピュート費は発生するため、ホスティング版は「無料」ではなく「安価な有料」として設計します。
