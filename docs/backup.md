# バックアップと復元

Banto のデータは 2 か所にあります。

| 何が | どこに | 自動バックアップ |
| --- | --- | --- |
| 商品・在庫・注文・会員・設定 | あなたの Supabase（PostgreSQL） | **Free プランには無い**。Pro（$25/月）は日次 7 日分 |
| 商品画像 | あなたの Cloudflare R2 | 無い（バージョニングも無い） |

Cloudflare Workers 上のコード自体は GitHub のリポジトリから何度でもデプロイできるので、バックアップは不要です。
Workers Secret（Stripe のキーなど）は Cloudflare にしか無いので、元のサービス（Stripe など）で再発行できれば十分です。

## 月に一度やること（無料プランの人）

1. 管理画面 → ショップ設定 → **バックアップ** → **すべてのデータを JSON で書き出す**
   - 商品・SKU・在庫・画像の一覧・注文・明細・会員・連携設定（hooks）が 1 つの JSON になります（`banto-<ショップ>-<日付>.json`）
   - 注文の CSV（Excel で開ける）も同じ場所からダウンロードできます
2. ダウンロードしたファイルを、手元のパソコンとは別の場所（Google Drive、OneDrive など）にも置く
3. 商品画像の元ファイルは、アップロード前のものを手元に残しておく

> JSON には購入者の氏名・住所・メールアドレスが含まれます。暗号化されたクラウドストレージに置き、不要になった注文の分は
> 管理画面の自動マスキング（発送から 180 日）と同じ考え方で、古いファイルは消してください。

## データが多いショップ（商品・注文・会員が数万件を超える）

管理画面の JSON の書き出しは、1 回の操作で全件を読みます。データが数万件を超えると Cloudflare Workers の 1 回あたりの上限
（CPU 時間・メモリ・外部への問い合わせの回数）に掛かって失敗することがあります。その規模では次の方法でバックアップしてください。

- **Supabase の自動バックアップ**（Pro プラン。データベースが 500MB を超える規模では、そもそも Pro が必要です）
- パソコンから `pg_dump` でデータベースを丸ごと書き出す（開発者向け。Supabase の画面 → Project Settings → Database の接続文字列を使う）

一覧の CSV は、今の検索の条件で新しい順に次の数までです。多いときは条件で絞って何回かに分けてください。

| CSV | 上限 |
| --- | --- |
| 注文（明細つき） | 2,000 件 |
| 会員 | 5,000 件 |
| 配布用のクーポンのコード | 10,000 件 |

## 画像のバックアップ

R2 の画像は管理画面からまとめてダウンロードする機能がありません（Workers のサイズ制限のため）。
次のどれかで対応してください。

- **元ファイルを残す**（いちばん簡単）: 管理画面がアップロード時に縮小するので、元の写真があればいつでも上げ直せます
- Cloudflare の画面 → R2 → バケット → オブジェクト一覧から個別にダウンロードする（枚数が少ない場合）
- パソコンで `rclone` や AWS CLI を使い、R2 の S3 互換 API で丸ごと同期する（開発者向け。R2 の「API トークンを管理」でトークンを作る）

## 復元

### Supabase Pro を使っている場合

Supabase の画面 → **Database → Backups** から日時を選んで復元できます（Pro は日次、Point-in-Time Recovery はアドオン）。
R2 の画像は消えていなければそのまま使えます。

### JSON から戻す場合（管理画面）

1. 復元先を用意する。**空のショップ**（商品も注文も無い）が必要です
   - 同じ Supabase で戻すなら、ダッシュボードから新しいショップを作る
   - 新しい Supabase プロジェクトなら、セットアップ画面を最後まで進めて最初のショップを作る
2. そのショップの **ショップ設定 → バックアップ → JSON から復元する** を開き、書き出した JSON を選んで **復元する**
3. 表示される件数を確認する（`products: 12, orders: 340, ...`）

復元の内容:

| 何が | どう戻るか |
| --- | --- |
| 商品・SKU・在庫 | 戻る。ID は新しく振られる（スラッグ・SKU コードは同じ） |
| 画像 | 一覧（R2 のキー）だけ戻る。**同じ R2 バケット**なら表示される。別のバケットなら元ファイルを上げ直す |
| 注文・明細 | 戻る。注文番号は保たれ、連番は最大値から続く。SKU が無い明細行は飛ばされる（件数に `order_items_skipped`） |
| 会員 | 戻る（同じ ID。0012 から会員はショップごとの行なので、別の Supabase プロジェクトにも戻せる）。メールアドレスの無い行・重なる行は飛ばされる（`customers_skipped`） |
| クーポン | キャンペーン・全体の上限の使用済みの数・発行済みのクーポン（コード・状態・期限）が戻る（0022）。対象の商品・カテゴリーはスラッグで付け直す。会員に発行したもので、その会員が戻らないものは飛ばす（`coupon_grants_skipped`）。**1 人あたりの使用回数は戻らない**（使用の記録は在庫の予約に紐づくため） |
| 注文の値引き・配送の指定・お問い合わせ番号 | 戻る（0022） |
| 取り込んだ過去の注文 | 戻る（0023）。取り込み元の ID・明細の品名、Banto に無い商品の明細も戻る |
| 連携（hooks） | 戻る。ID が変わるので **署名シークレットも変わる**。外部プラグイン側の設定を更新する |
| AI 用トークン | 戻らない。発行し直す |

ショップの設定（送料・テーマ・法務文書）は JSON の `shop` に入っていますが、自動では戻しません。ショップ設定画面に貼り直してください。

> 復元中にエラーが起きた場合は、途中まで入った分も含めてすべて取り消されます（1 つのトランザクション）。

## 書き出しの形

```json
{
  "banto_export": 1,
  "version": "0.0.1",
  "exported_at": "2026-10-14T00:00:00.000Z",
  "shop": { "id": "...", "slug": "my-shop", "name": "...", "settings": { } },
  "tables": {
    "products": [ ], "skus": [ ], "inventory": [ ], "product_images": [ ],
    "orders": [ ], "order_items": [ ], "customers": [ ], "hook_endpoints": [ ],
    "categories": [ ], "coupon_campaigns": [ ], "coupon_slots": [ ], "coupon_grants": [ ]
  },
  "counts": { "products": 12, "orders": 340 }
}
```

- 運営者の JWT（RLS が効く経路）で読むので、他のショップの行は入りません
- `coupon_slots` は全体の上限の「使用済み」の行だけです（上限の数だけ行があるため）
- AI 用トークン（`api_tokens`）はハッシュしか無いので入れていません。復元後は発行し直してください
- 復元は `restore_shop_data` RPC（`0006_ops.sql`、service_role のみ）で行い、管理画面が運営者の所有を確認してから呼びます
- `hook_endpoints` に外部プラグインの設定値は入りますが、署名シークレットはもともと DB にありません（サイトの秘密から導出）
