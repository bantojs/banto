# お問い合わせ（同梱モジュール）

お客様のお問い合わせをチケットにし、運営者とのやり取りを Banto の画面で続ける同梱モジュールです（既定 OFF。0061_mod_inquiries の適用が必要）。
設計の理由は docs/knowledge/14-inquiries.md。

**メールには本文を載せません。** お客様にも運営者にも、届くのは「お問い合わせがありました / 返事がありました」というお知らせと、チケットへのリンクだけです。
メールに返信してもらう仕組みもありません（返信は届きません）。やり取りはすべてリンク先の画面でします。
やり取りの中身がメールの事業者や転送先の受信箱に残らず、メールの送り手（Resend / SMTP / SendGrid / SES）のどれでも同じに動きます。

## 1. 使い方

1. メールの送り手と、メール通知プラグインの「送信元」を設定します（docs/email.md。会員のログインのメールと同じ設定です）。送信元が無いとお問い合わせを受け付けません。
2. ショップ設定 → モジュール →「お問い合わせ」を ON にします。
3. お問い合わせの画面の「設定」で、新しいお問い合わせを知らせる宛先を入れます（空ならショップの問い合わせ先のメールアドレス）。
4. 組織のスタッフに任せるときは、組織の画面でショップごとに「お問い合わせ」の項目を割り当てます（ひな形「お問い合わせの担当」）。この項目だけの人は、会員の一覧・CSV や注文の画面には入れません。

ON にすると、ショップの管理画面に「お問い合わせ」のタブが出ます。

## 2. お客様の画面

お問い合わせのフォーム（`/<ショップ>/inquiries/new`）は、お店の画面のどこからでも開けます（フッター・ログイン画面・会員ページ・注文照会・購入完了の画面）。お店の画面の使い方（docs/storefront.md）が「使わない」でも残ります。

- 入れるのは **種類**（商品について・注文 / 配送について・ログイン / 会員について・その他）、**内容**、お名前（任意）、注文番号（任意）。送る前に確認画面が出ます。
- **ログインしていない人**はメールアドレスも入れます。送ると、そのアドレスに確認のメールが届き、メールのリンクを開いた時点でお問い合わせが確定します（アドレスの持ち主だと確かめるため）。確定するまで運営者へのお知らせは送りません。
- **ログイン中の会員**は確認のメールなしで確定します。注文番号は自分の注文の一覧から選べます。会員ページに「お問い合わせの履歴」が出ます。
- **注文から**（注文照会の結果・会員の注文一覧・購入完了の画面の「この注文について問い合わせる」）は、注文が決まった状態でフォームが開き、返事のお知らせは**注文時のメールアドレス**に届きます（画面には出しません）。
- メールのリンクは 30 日有効です。リンクを開くと、その端末ではしばらくリンクなしで続きを読めます。リンクを無くしたら「リンクを送り直す」に受付番号とメールアドレスを入れます。
- 完了にしたお問い合わせには、お客様は書き込めません（新しいお問い合わせとして送ってもらいます）。

### 注文に結びつけるとき

- 会員の自分の注文、注文から開いたフォーム、ゲストが入れた注文番号と注文時のメールアドレスが合ったとき（注文照会と同じ判定）だけ、チケットを注文に結びます。
- 合わなければ、注文番号は「申告された注文番号」としてそのまま運営者に見せます（結びはしません）。他人の注文番号を書いて、その注文の情報を引き出させないためです。
- お客様には「番号とアドレスのどちらが違ったか」を見せません。

## 3. 運営者の画面

- 一覧: 対応中（ショップの返事待ち・お客様の返事待ち）・完了・未確認（アドレスの確認がまだ）で絞り込めます。
- 1 件: やり取り、連絡先（確認済みか）、会員に結びついているか、結んだ注文の要約（「注文・発送」の項目があれば注文の画面へ）。
- **返事を書く**と、お客様には「返事がありました」とリンクだけのメールが届きます。
- **未確認のお問い合わせ**にも返事は書けますが、送り主が本人とは限りません。注文の中身・住所・電話番号などを書かないでください（画面に警告が出ます）。
- 完了にする / 開き直す、削除（いたずら・削除の依頼）ができます。
- **定型文**: 設定で、よく使う返事を 10 個まで登録できます（「ショップの設定」の項目が要ります）。返事の欄の上で選んで「差し込む」と、`{name}`（お客様のお名前）・`{number}`（受付番号）・`{shop}`（ショップ名）を置き換えて入ります。
- **AI から**: AI 用トークンの `inquiries:read` / `inquiries:write` で、一覧・1 件・返事・完了ができます（docs/ai-access.md §8）。連絡先は `orders:pii` もあるときだけ渡します。

### 「ログインできない」というお問い合わせ

「メールアドレスを変えたのでログインできない、新しいアドレスに変えてほしい」は、なりすましの典型的な手口です。

- **お問い合わせのやり取りだけで、会員のメールアドレスを変えないでください。** 変更は今までどおり、会員の画面からだけできます（監査ログに残ります）。
- 古いアドレスにまだメールが届くなら、古いアドレスにログインのコードを送ってもらって本人だと確かめます。
- 古いアドレスがもう使えないときは、注文の内容（注文番号・金額・届け先の都道府県など、本人しか知らないこと）で確かめてから変えます。
- まずはお客様自身でできることを案内してください: 迷惑メールのフォルダの確認、コードの送り直し、使えるショップならパスワード・パスキー・LINE / Google でのログイン。

## 4. 個人情報と保持

- 連絡先とやり取りは運営者の Supabase に入ります。開発チームは触れません。
- 完了から `MASK_ORDERS_AFTER_DAYS`（既定 180 日）たったお問い合わせは、Cron が連絡先と本文を消します（受付番号と種類だけ残ります）。
- アドレスの確認がされないまま 30 日たったお問い合わせは消します（いたずら・打ち間違い）。
- 注文の画面の「この購入者の個人情報を削除（マスク）」（同じメールアドレスの注文・試着の申し込みを消す）は、そのアドレスのお問い合わせの連絡先と本文も消します。
- hooks（`inquiry.created` / `inquiry.updated`、docs/hooks.md）には個人情報を載せません。
- バックアップの JSON 書き出しと復元に含めます（docs/backup.md）。復元したお問い合わせは、メールのリンクが使えなくなります（お客様は「リンクを送り直す」で開き直す）。

## 5. 回数の上限

迷惑な投稿とメールの送りすぎを防ぐため、次の上限があります（ショップの設定 `settings.inquiries` の数字で変えられます）。上限を超えたときは「しばらくしてから」と出ます。

| 何を | 既定 | 設定の鍵 |
| --- | --- | --- |
| 同じ IP からのお問い合わせ | 1 時間 10 件 | `per_ip_per_hour` |
| ショップ全体のお問い合わせ | 1 時間 100 件 | `per_hour` |
| 同じメールアドレスの対応中のお問い合わせ | 5 件 | `max_open_per_email` |
| 同じ IP からの「注文を確かめる」「リンクを送り直す」 | 1 時間 20 回 | `checks_per_ip_per_hour` |
| 同じ宛先への確認・送り直しのメール | 1 時間 5 通・1 日 20 通 | （固定） |
| 運営者へのお知らせ | 1 時間 60 通 | `shop_notices_per_hour` |
| ショップ全体のお問い合わせのメール | 1 日 500 通 | `mails_per_day` |

お問い合わせのメールは、プランの 1 日のメールの上限（`plan_limits.mail_per_day`、docs/upgrade.md の 0053）にも数えます。

## 6. ヘッドレス

連携サイトの画面からも同じことができます（docs/headless.md「お問い合わせ」）。メールのリンクは、連携サイトの画面（決済後の戻り先と同じ許可リストのオリジンだけ）に向けられます。
