# 09. クーポン（値引き）の設計（2026-10-16）

運営者向けの手順は docs/coupons.md。ここは「なぜこうなっているか」と、次に作るものの設計。
**ここに書いた方針（判定はコア・混合型・方式 A・枠の取り合い）を変えるときは、先に人間に確認する。**

## 1. 置き場所（3 層の方針）

- **判定と回数はコア**（CLAUDE.md §7 の判定基準 (1) お金に関わる）。
  - 計算: `src/commerce/discounts.ts`（純粋な計算、DB に触らない）。`checkout.ts` の一本道（カート → quote → 確定）からだけ呼ぶ。同梱テーマもヘッドレス API も同じ判定を通る。
  - 回数: `0010_coupons.sql` の RPC。在庫の予約と同じ流れ（予約 → 確定 → 期限切れ・キャンセルで戻す）に相乗りする。
- **登録画面は同梱モジュール `coupons`（既定 OFF）**: `src/modules/coupons/admin.tsx`。OFF のショップではカートにも確認画面にも DB の往復を足さない（`couponSource()` が null）。
- 条件は **宣言型の JSON**（`coupon_campaigns.conditions`）。任意のコードは動かさない。条件を足しても表の作り直しは要らない。
  - 2026-10-23（0049）: 会員の独自項目（`attributes`、13-external-customer-master.md）を条件に足した。判定の材料は `coupon_lookup` に `p_customer_id` を渡して各行に `customer_attributes` を載せる（往復は増やさない。0049 が当たっているときだけ渡す）。値の検査は `banto_api_coupon_apply`（定義にある鍵だけ・select は選択肢の中）。ゲストには使えない。

## 2. 決めたこと（人間と合意済み）

- **混合型**: キャンペーン（マスタ = 値引きの内容と条件）に、使い方を 3 つ持たせる。
  1. 公開コード（**今回実装**）: コードを知っていて条件を満たす人なら誰でも。ゲストも使える。クーポン付きリンク（`?coupon=`）も。
  2. 会員に発行（配布型、次）: 発行済みクーポン（1 人 1 枚の行）を会員 ID に結びつけ、マイクーポンに入れる。確認画面で選ぶ。
  3. 使い捨てコード（次）: 発行済みクーポンを会員の代わりに 1 つの専用コードに結びつける（CRM・LINE 配信向け）。
  - 「メールアドレス限定」は **外した**（本人確認が弱い。他人のアドレスを知っていれば使える）。代わりに 2 か 3 を使う。
  - 「特定の会員だけ」は 2 で実現する。会員は **会員 ID で結びつける**（メールアドレスで結ぶと、変更で使えなくなる・古いアドレスで登録した他人が使える）。未登録の人をアドレスで指定したら「招待中」で持ち、そのアドレスで登録・ログインした時点で会員 ID に結びつける。
- **1 人あたりの回数・併用の可否をクーポンごとに設定できる**（人間の要望で最初の範囲に入れた）。
- **Stripe への渡し方は方式 A**: Banto が決めた値引きの額で Stripe のクーポン（定額・1 回限り、`banto_<額>_<名前のハッシュ>` で使い回す）を作り、Checkout Session の `discounts` に付ける。決済ページと領収メールに「クーポン CODE −¥500」と出る。
  - B（値引き後の単価で渡す）は単価が変わって見え端数も出る、C（Stripe のプロモーションコード）は判定が Stripe 側に移るので採らなかった。
  - KOMOJU は合計額だけを渡す方式なので影響なし。
  - Webhook で決済事業者が受け取った額（`amount_total` / `amount`）を `orders.amount_paid_jpy` に残し、Banto の合計と違えば管理画面の注文で知らせる。

## 3. 計算の規則（`evaluateDiscounts`）

- 最大 5 枚。入力順に判定し、併用できない組み合わせになるものは後から入れた方を外す。
- 計算の順は **割合 → 定額 → 送料無料**（入力順に関係なく）。割合は **値引き前の金額** にかける（複数の割合を掛け算で目減りさせない。WooCommerce の既定と同じ）。
- 割合と定額は **対象商品の金額にだけ** かかる。割合は 1 円未満を切り捨てる。値引きの合計は対象商品の金額を超えない。
- 値引きは **商品の行ごとに配分** する（最大剰余法。端数は端数の大きい行から 1 円ずつ）。注文の明細（`order_items.discount_jpy`）に残す。軽減税率とインボイスの領収書で、値引きを税率ごとに区分して書くための備え。
- 金額・点数の条件は対象商品だけで数える（値引き前・税込）。「○円以上で送料無料」の判定は値引き前の小計（今の動きを変えない）。
- **0 円の注文は決済なしで確定する**（人間の要望、2026-10-16）。`placeOrder` が予約・値引きの予約の直後に `confirm_reservation` を呼ぶ（`payment_provider = 'free'`）。支払いが無いので Webhook を待たない（CLAUDE.md §5 の例外。02-decisions）。金額は `recheckQuote` で引き直したもの。キャンセルは返金なしで `cancelled`、回数は戻る。
- 1〜49 円は確定しない（`minimum_amount`。Stripe の円の最低額は 50 円）。
- 確定時に判定し直し、quote と 1 円でも違えば（期間切れ・上限到達を含む）確定せず、確認画面を出し直す。

## 4. 回数の数え方と、遅くならない仕組み

WooCommerce でクーポンが増えると遅くなる原因（クーポンが索引の無い投稿・使用履歴をメタに溜めて数え直す・表示のたびに再計算・プラグインが全件を総なめ）を構造で避けた。

- キャンペーンは専用の表。コードは `(shop_id, code)` の一意索引で 1 回引く（`coupon_lookup`、service_role）。購入者の画面から表を直接読ませない。
- **全体の上限は「枠」の行**（`coupon_slots`、上限の数だけ作る）。確定の前に、空き枠を `FOR UPDATE SKIP LOCKED` で 1 つ取る。1 つのカウンターを全員で書き換えないので、先着のキャンペーンでも順番待ちが起きない。空き枠を探すのは部分索引（`status = 'free'`）。上限ちょうどで止まり、超えない（50 人同時のテストで確認）。
- **1 人あたりの回数**は `coupon_redemptions` の `(campaign_id, subject) where status <> 'released'` の部分索引で、その人の数行だけを見る。同じ人の同時の申込みだけ `pg_advisory_xact_lock` で直列にする（他の人は待たない）。
- subject は会員なら `c:<会員 ID>`、ゲストは `e:<メールアドレスの SHA-256>`。メールアドレスそのものは持たない。
- 判定するのはカート・確認画面・確定のときだけ。商品一覧・詳細はクーポンに触れない。
- 速度の予算（`test/perf-budget.test.ts`）: コードの入ったカートは 4 → 5 往復（`coupon_lookup` の 1 回）。クーポンが 1 件でも 2,000 件でも同じ。モジュールが ON でも、コードが無ければ増えない。
- 実 PostgreSQL のテスト（`test/db/coupons.test.ts`）で、キャンペーン 2 万件・使用の記録 2 万件・枠 3 万件のときに検索が索引を使う（全件を読まない）ことを実行計画で確かめている。

流れ（`placeOrder`）: `reserve_stock` → `attach_reservation_customer` → **`apply_reservation_discounts`**（枠と回数を予約し、値引きを予約に書く。取れなければ `coupon_*` で失敗し、予約ごと解放）→ 決済ページ。
確定（`confirm_reservation`）で使用済み、解放（期限切れの Webhook・Cron）とキャンセルで戻す。TTL 切れで解放された後に決済が完了したら、値引きはそのまま有効にし、空き枠があれば取り直す（無ければ上限を 1 回超える。購入者はもう支払っているため）。

- 配布型のマイクーポン（次）も、同じトークンで `/members/me/coupons` のように足せる。
