# 02. 設計判断と理由

CLAUDE.md に書いてある規約の「なぜ」と、規約には書ききれない運用上の判断。日付の新しいものが上。

## 2026-11-09

- **会員の社内メモ（メンテナの決定 2026-11-09）**: 注文には社内のメモ（`orders.note`、0106）があるのに会員には無く、「ギフト包装をよく頼む」「サイズ交換の履歴」のような申し送りを書く場所が無かったため。§7 の基準 (2) データの形 → コアは汎用の器だけ。扱いは注文のメモと同じにする。
  - 列は `customers.note`（2,000 字）。書くのは専用の RPC だけ（項目 `customers`）で、`customers` を直接更新させない。
  - 会員の hooks（`customer.updated`）には載せない。0050 の `banto_customers_hook` は列の許可リストで判定しているので、`note` をそこに足さない（プラグインの自己ループを防ぐのも注文の印・メモと同じ）。
  - 退会（行の削除）で一緒に消える。個人情報のマスク（`mask_customer`）でも消す（注文の `orders_mask_note` と同じく、メモに個人情報が入りうるため）。今の `mask_customer`（最新の定義は 0089）は注文・試着・お問い合わせを直すだけで `customers` に触らないので、メモを足すマイグレーションで定義し直し、同じショップ・同じメールの会員の `note` を消す。
  - バックアップの JSON 書き出しと空のショップへの復元（`restore_shop_data`）にはメモを含める（運営者のデータなので、移したら失われないように）。
  - AI 用 API は `customers:read` で読み、`customers:write` で書く（どちらも個人情報のスコープ。注文のメモが `orders:pii` のときだけ返るのと同じ考え）。
- **CSV の書き出しは列と範囲を選べる（メンテナの決定 2026-11-09）**: 注文・会員・商品の一覧で、範囲（この条件 / 選んだ行 / すべて）・列（まとまりごと、個人情報を含むまとまりに印）・1 行の単位（注文は注文ごと / 明細ごと、商品は SKU ごと / 商品ごと）・形式（Excel で開ける BOM 付き UTF-8 / UTF-8 / Shift_JIS）を選ぶ。よく使う組み合わせ（会計用・発送用・案内メールの宛先など）を用意する。
  - **「案内メールの宛先」の組み合わせは、案内メールに同意した会員（`marketing_consent = true`）の行だけに必ず絞る**。この条件は画面で外せない（特定電子メール法のオプトイン。同意のない宛先を案内メールのリストとして出さない）。同意の無い会員も含めたいときは、会員の一覧の普通の書き出しを使う。
  - **Shift_JIS への変換はブラウザで行う**（送り状 CSV と同じ。Worker の容量と CPU を使わない）。変換の部品は送り状 CSV のもの（`encodeSjis`）を共用し、Shift_JIS にできない文字（一部の旧字体・絵文字など）は同じ扱いにする: `?` に置き換えて書き出し、置き換えた文字を画面に並べて知らせる（黙って置き換えない。直したい人は元のデータを直すか UTF-8 で書き出す）。
  - **前回の選び方はそのブラウザに覚える**（DB には置かない。新しい鍵も `banto_shop_settings_perm` の登録も要らない）。
  - 実装（2026-11-10、DB は変えない）: 部品は `src/routes/admin/csv-export.tsx`（列の定義・選び方の読み取り・一覧の下の欄・ブラウザの側）。よく使う組み合わせは押すとすぐ書き出すボタン（注文: 会計用・発送用・売れた商品、会員: 案内メールの宛先・CRM に写す、商品: 商品の一覧・価格表・在庫表）。範囲「すべて」は条件を外した URL へ移す。案内メールの宛先は書き出しの側で `consent=yes` に必ず直す（範囲「すべて」でも外さない）。商品の CSV（`/products.csv`）は新しく作り、列を選ばなければ商品の一覧（SKU ごと）。注文・会員は、列を選ばない今までのリンク（「この条件で CSV」）を今までの列のまま残す。「選んだ行」の範囲は、一覧に行を選ぶ欄があるのが商品だけなので、まだ作らない。

## 2026-11-08

- **管理画面を作り直す（メンテナの決定 2026-11-08「おすすめでいこう」）**: 運営者から「管理画面が分かりにくい」。見た目より並べ方と言葉の問題だった（ショップ設定が 1 ページにカード 10 枚・保存ボタン 12 個、上のタブ 9 個にモジュール・プラグイン・Webhook・AI 連携が並ぶ、商品の編集の保存ボタンが 10 個、モジュールの説明に内部の言葉）。管理画面の容量は Worker の中で小さく（重いのはマイグレーションの SQL と 2 か国語の文言）、テーマ化（第三者のテンプレート）にしても容量は減らず、そのうえ運営者の JWT の画面で他人のコードを動かすことになるので採らない。全モジュール ON の前提で試作して決めた。
  - **目次は仕事ごと**: 毎日の運営（ホーム・注文・商品・会員・お問い合わせ・お店で試着）/ 集客（クーポン・お店のお知らせ・LINE・商品フィード・アクセス解析）/ お店づくり（デザイン・ページとブログ・貼れるタグ）/ 広げる（機能を追加・外部サービスと連携）/ ショップの設定。組織・実店舗・監査ログ・サイト・アップデートは右上のメニュー。モジュールは「モジュール」の奥に置かず、用途の近い場所に入れる（送り状 → 注文、採寸表・取り込み → 商品、お届け日時 → 配送と税、LINE・Google・パスキー → 会員とログイン、お店の行動 → 連携）。「機能を追加」は ON / OFF だけ。プラグイン・Webhook・AI 用トークンは「外部サービスと連携」の 1 画面にまとめ、入口は目的の言葉（アプリをつなぐ / 出来事を知らせる / AI に操作させる）。
  - **ショップ設定は分ける**: 基本と法定表記 / 配送と税 / 決済 / 会員とログイン / 領収書 / 上級者向け（独自ドメイン・お店の画面の使い方・ヘッドレス・バックアップ・確認画面の文言）。1 画面に保存は 1 つ。見た目（色・ロゴ・紹介文・お知らせ）はデザインへ。商品・会員の独自項目は書式の文字の欄ではなく表で決める。
    - 実装（2026-11-09）: 基本と法定表記はショップの URL（`/admin/shops/<id>`）のまま、ほかは `/admin/shops/<id>/settings/<画面>`。上級者向けは一覧から 1 つずつの画面（独自ドメイン・お店の画面の使い方・ヘッドレス・法務のページ・購入前の確認画面・商品画像・バックアップ）。画面に要る権限は保存する鍵の項目（0129）に合わせ、会員機能と商品画像・お店の画面の使い方・バックアップは owner / admin。今まで 1 つのフォームで送料と一緒に保存していた会員機能・商品画像の欄は、それぞれの画面の保存に分けた（settings の項目だけの人が送料を保存しても、owner / admin の鍵に触れない）。お届け日時は「配送と税」、LINE・Google のログインは「会員とログイン」から入り、画面の中のタブには出さない。独自項目は表にするまで今の書式の欄のまま、商品・会員の中の画面に移した。古い `#members` などのページ内リンクは使っていない（ブラウザのブックマークは基本と法定表記に着く）。
    - 独自項目の表（2026-11-09）: 商品・会員の項目は 1 行 1 項目の表（表示名・鍵・種類・選択肢・お客様の画面・消す）。**今ある項目の鍵は変えられない**（値の保存の名前なので、変えると入力済みの値と切れる。変えたいときは新しい項目を足す）。種類は選ぶだけ、選択肢は「,」「、」で区切る（「/」は値に使えるようにした）。今ある行は表示したときの選択肢を隠しの値でも送り、欄を触っていなければ元の配列のまま（区切りの文字を含む選択肢が、ほかの行を直しただけで分かれて商品の値が選択肢から外れないように。含む行には欄の下で知らせる）。空の行 3 つでスクリプトなしでも足せ、スクリプトがあれば「項目を足す」で行を増やす。形の違う鍵・重なる鍵があれば何も保存せずに知らせる（今までは黙って捨てていた）。行の並べ替えはまだ無い（定義の順のまま）。実店舗とブログの記事の項目は書式の文字のまま（組織・ブログの画面で、件数が少ない）。
    - 検索の形（2026-11-09、0132）: 部品は `src/routes/admin/search.tsx`（キーワード・並び・＋ 条件・チップ）。注文と商品の一覧から。条件がひとつでもあれば DB の `admin_search_ids` がすべて絞り（RLS の外で項目を 1 回確かめ、id だけ返す 0059 の形のまま）、無ければ今までどおり RLS 越しに新しい順。キーワードは「入れたものを読み取る」: 注文は `#番号`・番号・決済の参照・送り状番号（ハイフンを無視）が完全一致、電話番号は数字だけにして完全一致（一部では探さない。番号の一部で他人の注文が並ばないように。日本の国番号 +81 は 0 に読み替え、「+81 80 …」と「080-…」を同じにする。0134 からは「+81 (0)90-…」の括弧の 0 も吸収する）、メール・氏名は部分一致。商品は品番・JAN が完全一致、名前・スラッグは部分一致。日付は日本時間の日。並びは新しい順と古い順だけ（金額・名前の順はキーセットの鍵が変わるので後で）。形の違う条件は捨てる（URL から作るので、壊れた URL でもエラーにしない）。会員・お問い合わせへの組み込みとビューの保存（`views_set`）は次の段階。
    - ビュー（2026-11-09、0135）: 保存するのは条件の URL の値（`{ name, query }`、1 画面 20 個・全体で 8 KiB・名前 40 字・条件 12 個・値 100 字。形は DB が確かめ、意味は画面と `admin_search_ids` が確かめる）。書くのは「1 つ足す（同じ名前は置き換え）」の `views_add` と「名前で 1 つ消す」の `views_remove` で、並び全体を Worker から送らない（DB の中でショップの行を押さえて今の値から作るので、同時に保存しても片方が消えない）。8 KiB の上限は、権限の低いメンバーがビューだけで設定全体の上限（64 KiB、0129）を埋め、ほかの人の設定の保存を止めないため。開くとその条件の一覧の URL になり、スクリプト無しで動く。タブは「すべて」と保存したビューで、今の条件と同じビューに印を付け、同じでなければ「この条件をビューに保存」を出す。保存のあとに戻る先は画面の種類から決め、URL を送らせない。お問い合わせの一覧も同じ検索の形にした（キーワードは #番号・名乗った注文番号の完全一致か、連絡先のメール・名前の部分一致。件数が少ないので RLS 越しに読む、新しい 200 件まで）。
    - 会員の集計と詳細（2026-11-09、0133）: 集計は注文の表の文単位のトリガー（遷移表）で、変わった会員だけ数え直す（`banto_customer_stats_refresh`）。会員の行を作ったときも数える（復元は注文が先に入るため。Worker から数え直しを呼ばずに済む）。集計の列だけの変更では `updated_at` を動かさない（`banto_customers_updated_at`）。会員の詳細の画面（`/customers/<id>`）に、集計・注文（項目 orders の人）・お問い合わせ（support）・独自項目・社内メモ・案内メールの同意・アカウントの操作（メールアドレスの変更・パスキー・お気に入り・削除）を集め、一覧の行の「操作」はやめた。会員の検索も注文・商品と同じ形（キーワード・独自項目の値・同意・古い順）。社内メモの AI 用 API（`customers:read` で読み、`customers:write` で書く）・集計での絞り込みと並び替え・ログインの方法の表示（`member_identities` は運営者に読ませていない）は後の段階。
  - **ホームと権限の見え方**（実装 2026-11-10、0139）: ショップのホーム `/admin/shops/<id>/home` を目次のいちばん上に置き、組織のダッシュボードのショップ名もここへ。「今やること」は DB の `shop_home` の 1 回で数え、**見る人の項目にある分だけを返す**（出荷の担当に売上を出さない。鍵ごと返さないので、画面が間違えて出すこともできない）。1 件以上のものだけを、その条件の一覧へのリンクにする。開店の準備（法定表記・公開中の商品・ショップの公開）は owner / admin だけ、全部済んだら出さない。**見えないものは出さない、押せないものは理由を出す**: 注文の詳細のキャンセルは orders_cancel、個人情報の削除と会員を開くのは customers が無ければ、ボタンの場所に「『…』の項目が要ります」。リンクをもらってショップに入れるが項目の無い画面に来たら（`loadShop` が項目の不足で断った GET の 404）、どの項目が要るかを出してホームへ戻れる 403 の画面にする（`src/routes/admin/denied.tsx`）。触れないショップ・無いページは今までどおり 404。注文の詳細は支払いと発送を分けて見せ（状態は 1 つのまま、見せ方だけ）、経過（注文・発送）を出す。
  - **連携の詳細は目的の言葉で**（実装 2026-11-10、DB は変えない）: スコープ（AI 用トークン・つなぐ確認）と出来事（知らせる先）を、目的ごとのまとまり（商品・注文・会員・販促・お問い合わせ・ページとテーマ・ショップ／注文・会員・商品と在庫・機能）と言葉で見せ、スコープ名・出来事の名前は小さく添えるだけ（部品は `src/routes/admin/purposes.tsx`、どれもちょうど 1 つのまとまりに入ることをテストで縛る）。個人情報に触れるスコープ（orders:pii・customers:*）には印。自分の項目に無いスコープは理由つきで選べない（判定の正は今までどおり DB）。AI 用トークンは目的のひな形（商品の登録・注文を読む・テーマを CLI で公開・自分で選ぶ）から始めて細かく直す（`?preset=`、スクリプト無し）。知らせる先の詳細は「許していること」「受け取っている出来事」を先に出し、このアプリに送った履歴（送り直す時刻つき）、外す（トークン・接続・置いたデータも消える、と確かめてから）を一番下に分ける。
  - **店舗のスタッフのホームと営業時間の入れ方**（実装 2026-11-10、DB は変えない）: 実店舗ごとのホーム `/admin/stores/<id>/home`（スマホ向け）。今日の来店予定・取り置き中・届くのを待っている数と、対応中の申し込みのカード。取り置き中は片手で押せる大きなボタン（購入された / されなかった、高さ 44px 以上）で、押したらホームへ戻る。店舗に届いた（取り置き）は期限を選ぶので申し込みの画面へ。EC の在庫に戻すボタンは出さない（実店舗のスタッフには戻させない、のまま）。ショップが無く実店舗が 1 つだけの人は、管理画面を開くとこのホームへ。営業時間は、曜日ごとに「営業 / 定休日」と時刻の欄（休憩をはさむ 2 つ目も）、臨時休業・臨時営業は今ある日を 1 行ずつ（消す印つき）と、日付を選んで「休み / 時間を変える」を足す行、まとめて貼る欄は開いて使う。保存の形（曜日ごとの時間・臨時の日）と読み方（`parseRanges`・`parseSpecialDays`）は今のままで、欄を今までの書式に直してから同じ関数で確かめる（今までの文字の欄も受け付ける）。
  - **機能を追加の分類と言葉**（実装 2026-11-10）: 「モジュール」の画面の名前を「機能を追加」にし、使う仕事ごとのまとまり（注文・発送 / 商品 / 会員とログイン / 集客 / お客様対応 / ページとブログ / 外部サービスと連携）の見出しの下に並べる（`src/modules/registry.ts` の `category`、どの機能もちょうど 1 つ）。画面は ON / OFF と開くだけ。画面の文言から内部の言葉（「モジュール」「コアの一本道」・マイグレーションの名前）を外す（`test/admin-modules-categories.test.ts` が ja の文言全体で縛る）。コードとドキュメントの中では「同梱モジュール」のまま（設計の言葉なので）。
  - **ページ・記事の編集の画面は変えない**: 今の画面（WordPress のブロックエディタに倣った作り）を使う。作り直すのは入る道と枠だけ。
  - **検索は 4 画面（とクーポン・ページ・記事・試着・監査ログ）で同じ形**: キーワード 1 つ（入れたものを読み取る: `#番号`・メール・電話・送り状番号・品番・JAN）＋ 条件のチップ ＋ ビュー（よく使う条件の保存）＋ 並び替え。CSV は条件のまま。絞り込みは DB の検索の関数（0059 を広げる）で、1 ページ分だけ読む。スクリプトが無くても、条件はフォームの GET・チップは条件を外した URL として動く。
  - **保存したビューはショップのメンバーで共有**（人ごとにしない）。小さな店では見方をそろえるほうが便利で、新しい表が要らない（ショップの設定に置く）。鍵は **`settings` のいちばん上で画面ごとに分け**（`views_orders`・`views_customers`・`views_products`・`views_inquiries`）、**保存できるのはその画面の項目を持つ人**（注文のビューは orders、会員は customers、商品は catalog、お問い合わせは support）。settings の人だけにすると、出荷の担当が自分たちのビューを作れないため。`banto_shops_guard` はいちばん上の鍵ごとに項目を確かめる（中の鍵まで見るのは `modules` だけ）ので、`views` の中に画面ごとの鍵を入れる形にはしない。**ビューを書くのは専用の RPC**（例: `views_set(p_shop_id, p_screen, p_views)`。security definer で `banto_shop_perm(p_shop_id, <その画面の項目>)` を確かめ、`views_<画面>` の鍵だけを書き換える。ひな形の割り当て `page_layouts_set` と同じ形）。member が `shops` の行を直接更新するには RLS の `shops_member_update`（0024）が settings の項目を求め、0129 の鍵ごとの確かめはその上に足す仕組み（代わりに通す仕組みではない）なので、直接の更新では「orders だけの出荷の担当」が保存できないため。鍵は `banto_shop_settings_perm`（0129）にも画面の項目で登録し、直接の更新に対する守りとして残す（守り `banto_shops_guard` は今のまま）。`views_*` はお客様の画面に渡る設定の許可リスト（`banto_shop_public_settings`）に入れない。
  - **電話番号・送り状番号でも注文を探せる**（`orders` の項目の人）。メールで探せるのと同じ扱い。

- **注文の印（タグ）と社内のメモ（メンテナの決定 2026-11-04、0106）**: 規約 §7 の基準 (2)（データの形 → コアは汎用の器だけ）。管理画面の手作業（要確認・ギフト包装・電話済み）でも、外の道具（MA・CRM・n8n）が「処理済み」を付けて二重に処理しないのにも使う器で、判定の機能は持たない。印は自由入力（ショップで一覧を決める形にしない。迷わせないため）。メモには個人情報が書かれがちなので、AI 用 API では `orders:pii` のときだけ読み書きし、個人情報のマスキングで一緒に消す。印・メモの変更では hooks を出さない（印を付けたプラグインがその印でまた動く自己ループを防ぐ。要るなら後で `order.updated` を足す）。量が多いので監査ログにも残さない。

- **SKU・商品の画像・在庫の変更でも product.updated を送る（2026-10-29、0075、docs/hooks.md）**: 連携サイト（WordPress など）が商品をキャッシュしていると、SKU の価格・在庫・画像だけを変えたときに知らせが届かず、表示が古いまま残る。プラグインの側では気づけないので Banto が送る。積むのは DB のトリガー（管理画面・AI 用 API・取り込み・復元のどれでも同じ）。在庫は人の操作（運営者の JWT・AI 用トークン）と「ゼロ ⇄ あり」の切り替わり（購入で売り切れた・期限切れの予約が戻って再入荷した）だけにし、購入で数が減っただけでは送らない（注文のたびの知らせは多すぎる。少なくなったことは inventory.low。メンテナの決定 2026-10-29）。inventory.low のペイロードには product_id を足す（SKU から商品を引き直さなくてよいように）。まだ送っていない同じ商品の知らせには重ねない（一括の取り込みで 1 商品 1 通）。
- **テーマの CLI は npm のパッケージにしない（メンテナの決定 2026-10-29、docs/themes.md「コマンドから」）**: `cli/banto-theme.mjs` は依存のない 1 ファイルなので、Banto のリリースのタグから取ってテーマのリポジトリに置く。CLI が話す REST（`/api/v1/themes`）は Banto の版と一緒に変わるので、運営者が動かしている Banto と同じ版のファイルを使うのがいちばん食い違わない。npm に出すと、公開の権限・鍵の管理と、パッケージの乗っ取りの入り口が増える割に、得るものが少ない。テーマを作る人が増えて、版をまたいで使える形（API の版の取り決め）が要るようになったら考え直す。
- **AI 用 API で出したテーマのプレビューは、お店のオリジンから切り離す（2026-10-29、0074・docs/themes.md）**: プレビューの券は開いた人に結ばれない（リンクを渡せばだれでも開ける）。`theme:write` だけのトークンで作った券のまま同じオリジンで描くと、公開（`theme:publish`）を通らない版の JS が、リンクを踏んだ買い物客の会員の Cookie で動く。そこで API の券のプレビューは CSP の `sandbox`（`allow-same-origin` なし）で描き、レジはテーマで描かない。管理画面の design の人が作った券は切り離さない（カート・レジまで確かめる道を残す）。券に作ったところ（`admin` / `api`）を入れ、印の無い券は切り離す側に倒す。あわせて、公開していない版の資産は覚えさせない（中身を置き換えられるため）。
- **テーマの設定の画面の入れ物はプロトタイプを持たない（2026-10-29）**: セクション・ブロックの id はテーマのファイルから来るので、`__proto__`・`constructor`・`prototype` を id として受け取らず、鍵を作る入れ物は `Object.create(null)`、取り込みでも JSON の鍵 `__proto__` を断る。触っていない欄は検査せずに元の値のまま（画面で直せない `shopify://` の値を壊さない）。

## 2026-10-28

- **Liquid のテーマ（メンテナの決定 2026-10-28、0071、docs/themes.md）**: 小さなお店が、Worker を配置し直さずに見た目を少しずつ直し続けられるようにするため。今の TSX のテーマは、改造するとフォークになり、ホスティングの構成では開けない。§7 の基準 (2) データの形 → コアは器（版の表と置き場）と描画の一本道だけ。テーマは渡されたデータを描くだけ（§11「テーマはデータ取得をしない」のまま）。
  - **言語は Liquid**（liquidjs、版を固定）。閉じたテンプレート言語で、`eval` / `new Function` を使わない（Workers は禁じている）。Shopify のテーマを書ける人が書けるように、オブジェクト・フィルター・タグの名前を Shopify に合わせる。名前と使い方だけを合わせ、Shopify の文章・テーマのコードは持ち込まない。
  - **描画は同期だけ**。liquidjs の非同期の描画は同じテンプレートで 7 倍ほど遅い（generator と Promise の重さ）。テーマは版ごとに 1 つのファイルに束ね（ファイルごとに読むとサブリクエストが増える）、isolate のメモリに置き、データは描く前にそろえる。
  - **無料プランは TSX の既定のテーマだけ、Liquid は有料プラン（と Node）**。Shopify の公式の無料テーマほどの重さだと、商品カード 24 枚で CPU 14〜17ms かかり、無料プランの 10ms に収まらない。有料プランなら問題ない。
  - **既定でエスケープ**（`escape` / `escape_once` は二重にしない、生は `raw`、本体が作った HTML だけ `SafeHtml` で素通し）。テーマを書く人の書き間違いで XSS にしない。
  - **描画の手数を Banto が数えて止める**。liquidjs の時間の上限は時計で測るが、Workers は計算のあいだ時計が進まないので効かない。配列の入れ子のループは量の上限でも止まらない。
  - **描けないときは既定のテーマで描く**（テーマが壊れている・上限を超えた・その種類のテンプレートが無い・無料プラン・Banto の URL）。セクションの中の誤りはそのセクションだけを空にする（上限を超えたときはページごと既定のテーマへ。セクションを空にして続けると 1 ページで何度も上限まで回せる）。SEO の要（canonical・noindex・構造化データ）は本体が `content_for_header` に入れ、テーマが書き忘れても `</head>` の前に入れる。
  - **取り込みは zip をブラウザで開く**（ライブラリなし、zip の目次と `DecompressionStream("deflate-raw")`）。Worker は束ねた JSON を検査してから置き、資産は 1 つずつ（名前は束ねたファイルにあるものだけ、HTML・SVG は受けない）。Worker で zip を開くと CPU と取り込みの大きさの上限がきつい。**プレビューは署名付きの券**（ショップ × 版、30 分）をショップのドメインの Cookie で続け、`noindex`・`no-store`。プレビューの版の設定の値は既定値（設定の画面は後の段階）。
  - **金額は Shopify と同じく 100 倍の整数**（¥1,200 = `120000`）。Shopify のテーマを書く人が `| money` と算数をそのまま使えるように。メニューはカテゴリーの木から作る（Banto はメニューを持たない）。
  - **独自ドメインのショップだけ・権限の項目 `design`**。テーマの JS とエスケープしない出力は、お店の画面のオリジンで動く。独自ドメインの無いショップのお店の画面は管理画面と同じオリジンにあるので、テーマの JS が管理画面を操作できてしまう。管理画面は独自ドメインでは出さない（`src/routes/storefront/domain.ts`）ので、独自ドメインに限れば `design` の項目を owner / admin 以外にも渡せる。同じ理由で、テーマのファイル（`themes/`）は Banto の URL の `/media/` から配らない。公開中の版は `theme_publish` だけが変える（`settings` の項目で `shops` を直接書き換えさせない、トリガー）。

- **SKU を分ける軸（メンテナの決定 2026-10-28、0065）**: 商品によって SKU の分け方が違う（カラー × サイズ・型番だけ・型番 × 長さ）のに、SKU の `options` は自由な鍵で、表記が混ざり（色 / カラー）同じ組み合わせも作れたため。§7 の基準 (2) データの形 → コアは汎用の器だけ。

  - **守るのは DB**（SKU のトリガー: options の鍵が軸とちょうど同じ・値が空でない・同じ組み合わせは 1 つ。商品のトリガー: 軸を変えるとき今の SKU が合うこと）。値の候補は入力と一括作成のためで守らない（候補に無い色を足すたびに軸を直させない）。

  - **値の入力は区切りの文字を読まない**（メンテナの決定 2026-10-28）。値の候補はチップ（正体は 1 行に 1 つの textarea、スクリプトが無ければそのまま）、軸を決めていない SKU の選択肢は 1 行に 1 つ（`サイズ=M`）。カンマ・読点で区切ると `1,000mm` のような値が割れるため。区切りは値に入らない改行だけにする。

## 2026-10-26

- **データは 10 万件で必達、100 万件を目標にする（メンテナの決定 2026-10-26）**: 商品・SKU・クーポン・会員・注文のどれも、それまでは「小規模ショップ前提で全件を読んでメモリで処理する」作りで、PostgREST の 1 回 1,000 行（`max_rows`）を超えると**黙って欠けていた**（商品ページの在庫が 0 に見える、カートから商品が消える、一覧の 1,001 件目以降が出ない、管理画面の一覧が欠ける）。
  - **原則: リクエストの中で扱う行の数を、データの総数に比例させない**。一覧・検索・件数は DB で絞り込み・並べ替え・数え、Worker は 1 ページ分を受け取って描くだけ。PostgreSQL は 100 万件でもインデックスがあれば同じ速さで返す。Workers の CPU 10ms・メモリ 128MB・1 リクエストの外部呼び出し 50 回（無料プラン）に収まるのはこの形だけ。
  - **100 万件は運営者の Supabase が有料プランの前提**。商品 1 件（SKU・画像 3 枚・在庫・インデックス込み）でおよそ 3KB、100 万件で約 3GB になり、無料プランの DB（500MB）を超える。コードの制約ではなく契約の話なので、docs で案内する。
  - **検索は pg_trgm**（式インデックス `banto_product_search_text`: 名前・ブランド・タグ・説明の先頭 300 文字を小文字に）。Supabase と素の PostgreSQL（contrib）の両方にある。C.UTF-8 の DB で日本語からも 3 文字組を作れることを確かめた（test/db/product-listing.test.ts）。2 文字以下の語はインデックスが効かず、商品が多いと遅い。足りなければ PGroonga を検討する（セルフホストの PostgreSQL にも入れてもらうことになるので、そのときに改めて決める）。説明は先頭 300 文字だけ（全文を入れるとインデックスが大きくなりすぎる）。
  - **ページ送りはキーセット（cursor）**。`offset` は 100 万件の後ろのページで遅くなるので 10,000 までに制限し、公開 API に `cursor` / `next_cursor` を足した（docs/headless.md）。`total` は 10,000 まで数える（超えたら `total_capped`）。お店の画面は 48 件ずつ「次のページ」で、2 ページ目以降は検索エンジンに載せない（商品はサイトマップで載る）。
  - **並べ替えの値を商品に持つ**: `products.list_price_jpy` / `list_compare_at_jpy`（いちばん安い SKU の価格と、その SKU の通常価格）。価格順で並べるのに SKU を毎回集計できないため。SKU の文単位のトリガーで保ち、変わると商品の `updated_at` も進む（`updated_since` の同期に価格の変更が載る。それまでは載らなかった）。在庫は写さない（§6「在庫の正は inventory の 1 行」のまま）。名前順は DB の照合順（それまでの Worker の `localeCompare("ja")` とは漢字の並びが違う）。
  - **タグ・カテゴリーの件数は数え済みの表**（`product_facets`）。100 万件を毎回 GROUP BY できないため。商品の文単位のトリガーで差分を足し（1 文で何行入れても 1 回）、カテゴリーの木が変わったらそのショップのカテゴリーの件数を作り直す（管理画面の操作なので数秒かかってよい）。減る分では行を作らない（ショップの削除の連鎖の途中で、消えていくショップの行を作らないため）。
  - **0058 より前の DB では今までどおり全件を読んでメモリで**（`migrated()`、§11「コードと DB の版のずれ」）。応答の形は同じで、cursor の中身だけ offset になる。（v0.3.0 で消した: 土台が 0061 に進んだ）
  - 速度の予算: お店の画面と公開 API の一覧の初回は 6 → 5 回（全件の 3 回が「1 ページ」と「件数」の 2 回に）。
  - 大規模の性能テストは実 PostgreSQL の DB テストだけで回す（CI の時間を延ばしすぎないため）。

- **ストアフロントの URL は `/slug`（2026-10-17、人間と検討した方針）**: 人間の問い「Supabase も Vercel もプロジェクト / デプロイごとのサブドメインなのに、なぜ `/slug` か」への検討。
  - **`/slug` にした理由**: (a) Deploy ボタン直後の `banto.<アカウント>.workers.dev` ではショップごとのサブドメインが作れない。サブドメインには運営者のドメイン・ワイルドカード DNS・Worker のルート（`*.example.com/*`）が要り、対象の利用者（レンタルサーバーの WordPress を運用できる人）が初日につまずく。(b) 1 デプロイ = 1 運営者・複数ブランドなので、本番の顔はショップごとの独自ドメイン（0015、`domain.ts` が Host からショップを引き、中でスラッグを足す）。`/slug` は独自ドメインを当てるまでの住所とプレビュー。(c) 管理画面・API・ショップが同じオリジンで、Cookie・CORS・OAuth の戻り先が単純。

- **Banto の立ち位置は「ヘッドレス・コマースのバックエンド + 既定のストアフロント 1 本」**。表示（一覧・詳細・LP・SNS）は連携側が自由に作り、カートから先（在庫予約・送料・配送先・特商法・決済・注文確定・注文照会・会員）は Banto が手放さない。同梱テーマはレジを含む参照実装なので捨てない。連携側の作り方は docs/headless.md。
- **CRM を顧客マスタにして Banto から個人情報を抜く構成は採らない**。CRM は hooks の送信先（外部プラグイン）、個人情報は `orders:pii` スコープ経由のまま。小規模事業者に外部 SaaS の契約を前提にさせない。
- **取り置きは「店頭受け取り（決済済み、配送方法の一種）」だけをやる**。決済なしで在庫を日単位で押さえる形は、注文が Webhook でしか確定しない設計と衝突するので、やるなら単独の設計書から。
- **LINE LIFF 購入・ギフト・買い増し・請求書払いはコアに入れない**（外部プラグイン案件か、個別設計）。理由: LINE LIFF の購入は LINE Login・LIFF・Messaging API でひとつの製品の規模で、hooks と API だけで外から作れる。ギフト・買い増しは在庫の不変条件か「カード情報を扱わない」に触れる。請求書払いは「未入金の注文」という状態を足す話で小さくない。

## 2026-10-15

- **マイグレーションは Supabase Management API 経由を既定にした**（`src/db/migrate-api.ts`）。Workers から Supabase の pooler に TLS で直接つなぐと、ハンドシェイク直後に切られる（workerd #2712）。接続文字列の経路（`src/db/migrate.ts`）は Node 実行とローカル Supabase 用に残す。Hyperdrive は §1-2 で禁止。
- **運営者の初回作成は GoTrue Admin API で確認済みユーザーを作る**。signup だと確認メールのリンク先が Supabase の Site URL（既定 localhost:3000）になり、非技術者が詰まる。会員の signup は従来どおり（`redirect_to` を付ける）。
- **`wrangler.jsonc` に `vars` を書かない、`keep_vars: true`**。空の `vars` を書いていると、ビルドのたびに wrangler が画面で入れた値を空で上書きする。必須の 3 値は `.dev.vars.example` に `REPLACE_ME` 入りで列挙し、Deploy ボタンの画面で聞かせる。`REPLACE_ME` と空文字は ConfigAdapter が「未設定」として扱う。
- **wrangler.toml → wrangler.jsonc**。Deploy ボタンで動作報告のある構成がすべて jsonc だったため。
- **Checkout の `expires_at` は 35 分、在庫予約の TTL はその 5 分後**。Stripe の下限はちょうど 30 分で、通信の遅れで弾かれる。
- **Cron の経路で `fetch` は必ずラッパー関数にして渡す**。Workers では素の `fetch` をオブジェクトのプロパティ経由で呼ぶと `Illegal invocation`。
- **決済プラグイン（Stripe / KOMOJU）は hooks のイベントを購読しない**。受信処理が無いので、購読すると配信が失敗し続ける。設定画面からイベント欄を消し、既に積まれた配信は 204 で完了扱い。
- **ロケールと時間帯はデプロイ単位**（`BANTO_LOCALE` / `BANTO_TIMEZONE`）。リクエストごとの切り替えは isolate 内で競合するので持たない。売上集計の日別・月別の区切りも `BANTO_TIMEZONE`（0076 で SQL に `p_time_zone` を足し、Worker が渡す。省略は Asia/Tokyo）。
- **Secret の形を管理画面で検査する**（`secretFormats`）。`sk_` と `whsec_` の取り違えが実際に起きた。
- **組織（Organization）の Stripe キーは `STRIPE_CONTEXT`（acct_…）で対応**。推奨はアカウント内で発行したキー。

## 2026-10-14

- **画像の縮小とサムネイルはブラウザ側**（canvas → WebP、1600px / 400px）。Cloudflare Images は固有機能、wasm は Workers Free の CPU 10ms に抵触。AI の URL 取り込みはサムネイル無し（テーマは本画像で代用）。
- **画像配信は R2 カスタムドメイン + `MEDIA_BASE_URL` を推奨**。Worker を通さないので無料枠の持ちが良い。既定（Worker 配信）でも動く。
- **バックアップは JSON 書き出し + 空ショップへの復元**（`restore_shop_data`、id 振り直し）。会員は同じ Supabase プロジェクトのときだけ戻る。
- **Cron の生存は `banto_heartbeats` + `/health` の `cron`**。全ジョブの最後に書くので、途中で落ちても stale になる。
- **英語 UI は `en.ts` にフル翻訳、キーの一致をテストで検査**。
- **外部プラグインの実例は本体のコードを読み込まない**（docs/hooks.md の契約だけで動く）。本体側のテストが署名の互換を検査。

## それ以前（v0.1 の骨格）

- Secret の受け渡しはコピー方式（運営者が Cloudflare の画面で貼る）。ウィザードは不足を検出して案内するだけ。
- Stripe は API キー方式が既定、Connect は上級設定。注文確定は Webhook のみ。
- 在庫の減算は Postgres の RPC だけ。予約 → 確定 → 解放。
- hooks の署名シークレットは DB に置かず導出。ペイロードに個人情報を載せない。
- AI 用トークンは `api_*` RPC だけを呼び、権限判定は SQL 側。
