# 02. 設計判断と理由

CLAUDE.md に書いてある規約の「なぜ」と、規約には書ききれない運用上の判断。日付の新しいものが上。

## 2026-10-28

- **Liquid のテーマ（人間の決定 2026-10-28、0071、docs/themes.md）**: 小さなお店が、Worker を配置し直さずに見た目を少しずつ直し続けられるようにするため。今の TSX のテーマは、改造するとフォークになり、ホスティングの構成では開けない。§7 の基準 (2) データの形 → コアは器（版の表と置き場）と描画の一本道だけ。テーマは渡されたデータを描くだけ（§11「テーマはデータ取得をしない」のまま）。
  - **言語は Liquid**（liquidjs、版を固定）。閉じたテンプレート言語で、`eval` / `new Function` を使わない（Workers は禁じている）。Shopify のテーマを書ける人が書けるように、オブジェクト・フィルター・タグの名前を Shopify に合わせる。名前と使い方だけを合わせ、Shopify の文章・テーマのコードは持ち込まない。
  - **描画は同期だけ**。liquidjs の非同期の描画は同じテンプレートで 7 倍ほど遅い（generator と Promise の重さ）。テーマは版ごとに 1 つのファイルに束ね（ファイルごとに読むとサブリクエストが増える）、isolate のメモリに置き、データは描く前にそろえる。
  - **無料プランは TSX の既定のテーマだけ、Liquid は有料プラン（と Node）**。Shopify の公式の無料テーマほどの重さだと、商品カード 24 枚で CPU 14〜17ms かかり、無料プランの 10ms に収まらない。有料プランなら問題ない。
  - **既定でエスケープ**（`escape` / `escape_once` は二重にしない、生は `raw`、本体が作った HTML だけ `SafeHtml` で素通し）。テーマを書く人の書き間違いで XSS にしない。
  - **描画の手数を Banto が数えて止める**。liquidjs の時間の上限は時計で測るが、Workers は計算のあいだ時計が進まないので効かない。配列の入れ子のループは量の上限でも止まらない。
  - **描けないときは既定のテーマで描く**（テーマが壊れている・上限を超えた・その種類のテンプレートが無い・無料プラン・Banto の URL）。セクションの中の誤りはそのセクションだけを空にする（上限を超えたときはページごと既定のテーマへ。セクションを空にして続けると 1 ページで何度も上限まで回せる）。SEO の要（canonical・noindex・構造化データ）は本体が `content_for_header` に入れ、テーマが書き忘れても `</head>` の前に入れる。
  - **取り込みは zip をブラウザで開く**（ライブラリなし、zip の目次と `DecompressionStream("deflate-raw")`）。Worker は束ねた JSON を検査してから置き、資産は 1 つずつ（名前は束ねたファイルにあるものだけ、HTML・SVG は受けない）。Worker で zip を開くと CPU と取り込みの大きさの上限がきつい。**プレビューは署名付きの券**（ショップ × 版、30 分）をショップのドメインの Cookie で続け、`noindex`・`no-store`。プレビューの版の設定の値は既定値（設定の画面は後の段階）。
  - **金額は Shopify と同じく 100 倍の整数**（¥1,200 = `120000`）。Shopify のテーマを書く人が `| money` と算数をそのまま使えるように。メニューはカテゴリーの木から作る（Banto はメニューを持たない）。
  - **独自ドメインのショップだけ・権限の項目 `design`**。テーマの JS とエスケープしない出力は、お店の画面のオリジンで動く。独自ドメインの無いショップのお店の画面は管理画面と同じオリジンにあるので、テーマの JS が管理画面を操作できてしまう。管理画面は独自ドメインでは出さない（`src/routes/storefront/domain.ts`）ので、独自ドメインに限れば `design` の項目を owner / admin 以外にも渡せる。同じ理由で、テーマのファイル（`themes/`）は Banto の URL の `/media/` から配らない。公開中の版は `theme_publish` だけが変える（`settings` の項目で `shops` を直接書き換えさせない、トリガー）。

- **レジ（配送先・最終確認）をテーマに開く（テーマの段階 3、人間の決定 2026-10-28、docs/themes.md「レジ」）**: Shopify が Plus に限るチェックアウトの途中の画面を、標準で開く。Shopify が限る理由（カード番号の画面の安全・全店の一斉の改良）は、Banto では決済がホスト型のページで判定が本体（`checkout.ts` の quote と確定の直前の引き直し）にあるので当てはまらない。§7 の基準 (1) 法務 → 表示はコアの部品。
  - **特商法の最終確認の表示は Banto の部品**（`src/themes/default/confirmation.tsx` の `ConfirmationBlock`、同梱テーマと共用）を `{% banto_confirmation %}` で置く。無いテーマは取り込まず、描いた結果に無ければ既定のテーマで描く（2 重に守る）。
  - **レジの画面は CSP `script-src 'self'`**（住所・連絡先が載るため、外とインラインのスクリプトを止める）。フォームの送り先は決済ページへの転送があるので縛らない。
  - 決済は今までどおりホスト型のページ（§1-6）。完了画面は今は既定のテーマのまま。

- **カート・検索・テーマのブロック・フォーム（テーマの段階 3、人間の決定 2026-10-28、docs/themes.md「カート」）**: Shopify のテーマがそのまま書ける範囲を広げる。判定（公開中の SKU・在庫・値引き・確定）は今までの一本道（`priceCart`・`discountCart`・`checkout.ts`）のままで、ここは書き方の読み替えだけ（`src/cart/shopify-form.ts`）。
  - カートの行の鍵は SKU の id（Banto のカートは SKU ごとに 1 行）。どのページでも `cart.items` を渡す（ヘッダーのカートの一覧。カートが空なら DB に問い合わせない）。
  - AJAX の `/cart.js` 系も同じオリジンだけ（`csrfGuard`）。`url_to_remove` は GET（Banto の購入リンク `/buy` と同じく、変わるのはこのブラウザのカートだけ）。
  - `form 'contact'` はお問い合わせの画面へ値を写して続ける（確認・メールの確認は Banto の流れのまま）。`customer_login` はメールのコードのログインへ（パスワードの欄は使わない）。

- **テーマの設定の値を管理画面で変える（テーマの段階 3、人間の決定 2026-10-28、docs/themes.md「設定を変える」）**: Shopify Plus と比べられるように、テーマの機能を段階 3 で全部入れる（設定の画面・カートと検索・ブロックとフォーム・レジ・Banto Cloud）。その 1 つ目。
  - 入力の形はテーマの宣言から作り（`src/themes/liquid/editor.ts`）、値は版の `settings`（0071 の器）に置く。テーマのファイルは変えない（版の中身は変わらない、監査とキャッシュの前提を崩さない）。新しいマイグレーションは要らない。
  - セクション・ブロックの値は `settings.__sections` に「置き場 → セクションの id」で、ファイルの値と違うものだけ。描くときに重ねる（`withOverride`）。並び・追加・削除は画面ではさせない（テーマのファイルで決める）。
  - `image_picker` はテーマの資産の画像から選ぶ（置き場に新しいファイルを足さない。外の URL も受けない）。

- **テーマをコマンドと CI から出す（テーマの段階 2、人間の決定 2026-10-28、0072、docs/themes.md「コマンドから」）**: テーマを Git で管理して、プルリクエストでプレビュー・main で公開したい（Shopify CLI と GitHub 連携に当たる）。§7 の基準: コアに足すのは AI 用 API のスコープと経路だけ（判定は既存の版の表と DB の関数）。
  - **スコープは 2 つに分ける**: `theme:write`（取り込み・プレビューのリンク・公開していない版の削除）と `theme:publish`（公開・取り下げ）。テーマにはお店の画面で動く JS を入れられるので、CI の秘密が漏れたときに公開中の画面まで変えられないように、プレビュー用のトークンには公開を付けない。どちらも項目 `design`（発行者が持つ間だけ効く）。公開・取り下げ・プレビューは監査ログにトークンとして残る。
  - **REST だけ**（MCP には出さない）。テーマの中身（数 MB のファイル）を AI の会話に通す使い方は想定しない。
  - **CLI は依存なしの 1 ファイル**（`cli/banto-theme.mjs`、Node 20 以上の fetch と fs だけ）。テーマのリポジトリに写して使える。npm への公開は後で人が決める。手元では描かない（`dev` も Banto に取り込んでプレビューのリンクを出すだけ）: 描画と検査を 1 か所に保ち、お店のデータを手元に持ち出さないため。
  - 管理画面の取り込みと API は同じ検査・置き場の処理（`src/themes/liquid/versions.ts`）を通る。資産を送り終える前に止まった版は CLI が消す（公開できない版が数の上限を埋めないように）。

- **ヘッドレスでパスキーを追加（人間の決定 2026-10-28、0070）**: パスキーの追加は Banto の会員ページ（ショップのドメインの Cookie のログイン）でしかできず、お店の画面を使わないショップでは追加の手段が無かったため。
  - 追加はショップのドメインの画面でしかできない（RP ID）。会員トークンで「券」を受け取り（2 分・1 回限り、トークンは HMAC だけを置く）、ブラウザをその画面へ送る。GET は確かめだけで、ボタンの POST で券を使う（URL が履歴・Referer に残っても、開いただけでは使われない）。
  - **券を出せるのはログインしてから 15 分以内の api のセッションだけ**（0057 の「盗まれたセッションから永続的なログイン手段を足させない」を崩さない）。券を使うときもそのセッションがまだ生きているかを確かめる。
  - 券を使うとショップのドメインに web のセッションを作る（作ったばかりなので、既存の追加の関数の 15 分の決まりをそのまま通る）。追加が済んだら取り消し、その端末に Banto のログインを残さない。
- **会員ページを連携サイトに（人間の決定 2026-10-28、0069）**: お店の画面を使わないショップでも、会員へのお知らせのメール（ログインがあった・パスワードを決めた）のリンクが Banto の会員ページに固定されていたため。注文照会のページと同じ形の設定を 1 つ足す（`account_page_url`）。パスキーの追加の知らせはショップのドメインのまま（パスキーはそのドメインに結びつく）。試着のメールのお店のリンクは、新しい設定を足さず、お店の画面の使い方の `site_url` を使う。設定の入れ漏れは AI 用 API の `GET /shop` で読めるようにする（連携側のプラグインのため）。
- **会員本人の操作をヘッドレスの会員 API に（人間の決定 2026-10-28）**: お店の画面を「使わない」にすると、会員が自分で退会・住所の保存・案内メールの選択をする手段が無かったため（個人情報の削除の求めに、本人が応えられない）。会員ページと同じ RPC（`member_withdraw`・`member_save_address`・`member_set_marketing_consent`）を、会員トークン（世代を確かめる）で呼ぶ。
  - 案内メールの「受け取る」（true）も許す。会員がログインして自分で選ぶので、0050 の「true は本人の行為だけ」の範囲（連携サイトのマイページにも欄が要る）。API 用トークン（運営者の道具）からは今までどおり false だけ。
  - 退会は取り消せないので `{ "confirm": true }` を求める。LINE / Google の連携・解除とクーポンの獲得ページは API にしない（ほかの道がある。獲得ページは登録画面で知らせる）。
- **お問い合わせの担当者（人間の決定 2026-10-28、0068）**: 複数の人で問い合わせを受けるショップで、誰が持っているかが分からず、返事が重なる・漏れるため。同梱モジュール inquiries の中（§7 の基準 (3) 使わない人が多い）。
  - 担当にできるのは support の項目を持つ人だけ（判定は SQL の `banto_user_shop_perm`）。項目を外されても割り当ては残す（自動で外すと、誰も持っていないチケットが黙って増える）。
  - 担当になった人にはリンクだけのメール（本文は載せない。お問い合わせのメールの決まりと同じ）。自分で自分に割り当てたときは送らない。
  - **未割り当てのチケットに最初に返事をした人を担当にする**（返事を書いた時点で事実上その人が持っているため。トリガーで、AI 用トークンの返事は人ではないので当てない）。ショップの既定の担当・順番に割り当てる仕組みは持たない（小さな店では要らず、要るなら hooks と API で外から割り当てられる）。
  - AI 用トークンからも読む・変える（inquiries:write）。返す運営者のアドレスは運営側の人のもので、orders:pii は要らない。
- **注文照会の回数の上限（人間の決定 2026-10-28、0067）**: ヘッドレスの注文照会の API が増え、番号とメールアドレスの組を当てに行く入口が広がったため。`lookup_order` は anon キー（公開の値）で直接呼べたので、Worker で数えるだけでは上限にならない。anon から外し、service_role の `order_lookup` が数える。
  - 数えるのは外れだけ（合った照会は何度でも通す。本人が何度も開くのを止めない）。同じ IP から 1 時間 20 回（ショップの設定）と、同じ注文番号へ 1 時間 50 回（IP を変えて 1 つの注文を狙うのを止める）。注文ごとの上限は第三者が外し続けるとその注文の照会を 1 時間止められるが、外れの数を大きく取り、時間で戻るので受け入れる。
- **注文照会・領収書をヘッドレスで（人間の決定 2026-10-28、0066）**: お店の画面を連携サイトで作るショップでも、注文照会と領収書だけは Banto の画面を開いてもらう必要があったため。§7 の基準 (1) お金・法務 → 判定（照合・税の計算・領収書を出してよいか）はコアのまま、画面は連携サイト。
  - **Banto はデータ（JSON）だけを渡す**。領収書も記載事項と税率ごとの内訳の計算結果だけで、レイアウト・宛名・印刷は連携サイトが決める（ショップごとに見た目を合わせたいため）。税の計算は `src/commerce/tax.ts` の結果をそのまま表示してもらう。
  - **外の URL は注文照会のページ 1 つだけ**（`settings.headless.order_page_url`、許可リストのオリジンの https）。注文メールのリンクと Banto の注文照会の画面の転送先に使う。領収書は注文照会のページから API で開くので、URL を別に持たない。
  - **メールのリンクに秘密を載せない**（`?banto_order=<番号>`、会員の注文なら `&banto_member=1`）。メールは転送・共有されるので、リンクだけで注文が開けると困るため。会員は会員トークン（ログインしていればそのまま開き、していなければログインしてから戻る。戻すのは連携サイトの仕事で、Banto を通るログインには `return_to`）、ゲストは番号とメールアドレス（今までの注文照会と同じ）。
  - **ゲストで買った注文は会員に結びつけない**（同じアドレスの会員でも）。アドレスの持ち主の確認と注文の持ち主が一致する保証が無いため。
  - 注文照会の回数の上限は 0067（上）。
- **SKU を分ける軸（人間の決定 2026-10-28、0065）**: 商品によって SKU の分け方が違う（カラー × サイズ・型番だけ・型番 × 長さ）のに、SKU の `options` は自由な鍵で、表記が混ざり（色 / カラー）同じ組み合わせも作れたため。§7 の基準 (2) データの形 → コアは汎用の器だけ。
  - **決める場所はショップ → カテゴリー（親から子へ）→ 商品**。使うのは主カテゴリーだけ（追加カテゴリーはセールの棚など、分け方を決める場所ではない）。
  - **上の段は「ひな形」として写す**（生きたまま引き継がない）。カテゴリーの軸をあとで変えたときに、在庫・注文の履歴・カートのある既存の SKU が一斉に決まりに合わなくなるため。商品を作ったとき・主カテゴリーを決めたとき（SKU がまだ無く、商品で上書きしていないとき）にトリガーが写す。変えたら「商品に当てる」（`option_axes_apply`）で、上書きしていない・SKU がそのまま合う商品だけに当て、合わない商品は名前を返す。
  - **守るのは DB**（SKU のトリガー: options の鍵が軸とちょうど同じ・値が空でない・同じ組み合わせは 1 つ。商品のトリガー: 軸を変えるとき今の SKU が合うこと）。値の候補は入力と一括作成のためで守らない（候補に無い色を足すたびに軸を直させない）。
  - 軸は 3 つまで（お店の画面で選ぶのは 3 段までが現実的）。`null` = 決めていない（今までどおり自由）、`[]` = 品番だけ。
  - WooCommerce の取り込み（`import_catalog`）は写さない（属性の鍵がカテゴリーの軸と合わないと取り込みが止まるため。0065 で包み、取り込みの間だけ写すのを止める）。取り込んだ後に「当てる」か商品の「今の SKU から推す」。
  - お店の画面は軸ごとの選択欄（スクリプト。無ければ今の 1 つの選択欄）。軸を決めていない商品も、SKU の項目がそろっていれば同じように出す。判定は `src/products/option-axes.ts`。
  - **値の入力は区切りの文字を読まない**（人間の決定 2026-10-28）。値の候補はチップ（正体は 1 行に 1 つの textarea、スクリプトが無ければそのまま）、軸を決めていない SKU の選択肢は 1 行に 1 つ（`サイズ=M`）。カンマ・読点で区切ると `1,000mm` のような値が割れるため。区切りは値に入らない改行だけにする。

## 2026-10-27

- **SDK は今は作らず、ヘッドレスの公開 API にも OpenAPI を出す（人間の決定 2026-10-27）**: 連携側の言語がばらばら（WordPress の PHP・Next.js・Python・ノーコード）で、言語ごとの SDK は保守が膨らみ、「SDK × コード × DB」の版のずれが増える。判定は Banto にあるので、連携側は送って表示するだけで足りる。代わりに `GET /api/openapi.json` で各言語のクライアントを生成できるようにする。文書は手で書き（`src/routes/api/openapi-public.ts`）、ルートとの食い違いはテストで止める。間違えやすい流れ（会員トークンの更新・カートのトークン・quote）の小さな JS の部品と、WordPress のブロックは、要望が続いたら。
- **お問い合わせの添付を AI 用 API（REST）で扱う（人間の決定 2026-10-27、0064）**: 運営者が外部のヘルプデスクや自前の画面から、Banto の管理画面を開かずにやり取りを続けたいため。0061 では「API には添付の中身を渡さない」としていたのを、REST だけ開ける。
  - **受け取りは `inquiries:read` と `orders:pii` の両方**（写真や書類は連絡先と同じく個人情報を含みうる。ファイル名を `orders:pii` のときだけ返していたのと同じ線）。返事への添付は `inquiries:write`。
  - **MCP には足さない**（AI にお客様のファイルの中身を渡さない。本文と同じくプロンプトインジェクションの入り口になりうるうえ、個人情報の量が増える）。
  - 判定（数・種類・大きさ・鍵の接頭辞）は管理画面と同じ `banto_inquiry_attach` と `src/modules/inquiries/attachments.ts`。先に置いて、断られたら消す流れも同じ。
- **SKU ごとの画像（人間の決定 2026-10-27、0063）**: WooCommerce のバリエーションの画像のように、カラー単位・カラー × サイズ単位で画像を結びたいため。§7 の基準 (2) データの形 → コアは汎用の器だけ。

  - **`/slug` にした理由**: (a) Deploy ボタン直後の `banto.<アカウント>.workers.dev` ではショップごとのサブドメインが作れない。サブドメインには運営者のドメイン・ワイルドカード DNS・Worker のルート（`*.example.com/*`）が要り、対象の利用者（レンタルサーバーの WordPress を運用できる人）が初日につまずく。(b) 1 デプロイ = 1 運営者・複数ブランドなので、本番の顔はショップごとの独自ドメイン（0015、`domain.ts` が Host からショップを引き、中でスラッグを足す）。`/slug` は独自ドメインを当てるまでの住所とプレビュー。(c) 管理画面・API・ショップが同じオリジンで、Cookie・CORS・OAuth の戻り先が単純。
  - **弱点**: 全ショップが同じオリジン。会員の Cookie は `Path=/:shop` で分けているが Path はセキュリティの境界ではない（同じオリジンの JS から読める、localStorage も共有）。今は「テーマは開発チームのコード・入力はエスケープ・見知らぬ他人同士は同居しない（CLAUDE.md §3）・隣のショップも同じ運営者」なので許容。ホスティングで他人同士が同じオリジンに並ぶと、1 か所の XSS が隣の店の会員セッションに及ぶので許容できない（Supabase・Vercel がサブドメインを切るのはオリジン分離のため）。

- **機能の置き場所を 3 層に分けた（人間が決定）**: コア（データの汎用の器 + 判定の一本道）/ 同梱モジュール（既定 OFF、コアの拡張点だけを実装）/ 外部プラグイン（hooks + API）。WooCommerce からの移行で要る機能（商品マスタの拡張、クーポン、フィード、インポーター、配送）を足してもコアを膨らませないため。詳細と判定基準は docs/ARCHITECTURE.md「プラグインアーキテクチャ」、計画は 08-woo-migration.md。
  - 今の同梱プラグイン（hooks の受け手）だけでは足りない理由: クーポンや送料はチェックアウト中に**同期で**金額に関わり（quote の照合を 1 か所に保つ必要）、カテゴリーやクーポンの利用回数は**テーブル**が要る。どちらも hooks ではできないので、コアに「拡張点」を用意し、モジュールがそれを実装する。
  - 開発チームが書いてレビューする自前のコードなので、「第三者のコードを本体に読み込まない」原則とは矛盾しない。
- **速度の予算を数字で検査する**: 主要ページの DB 往復回数（`test/perf-budget.test.ts`）と Worker の圧縮後サイズ（`npm run check:size`、上限 1 MiB。決定時点で 184 KB、無料プランの上限は 3 MB）。WooCommerce が遅くなる主因（プラグインが毎リクエスト動く）を構造で禁止し、数字で守る。
- **外部ライブラリは禁止しない。基準と予算で管理する**: 一律禁止にすると Shift_JIS（送り状 CSV）や PDF（インボイスの領収書）のように「作れない」か「無理に自作して品質が落ちる」になる。標準機能を優先、重い処理はブラウザ側でライブラリ可、Worker 側は可搬性・ネイティブ依存なし・テレメトリなしを条件に、サイズを PR に書く。
- **商品の分類はタグ（`products.tags text[]`）だけにした**。カテゴリの木構造は持たない（小規模事業者には過剰、WordPress 側の表示はタグで足りる）。1 商品 20 個・1 個 40 文字、正規化は SQL（`banto_normalize_tags`）と TS（`src/products/tags.ts`）で同じ規則。タグの件数順の同数は文字コード順で並べる（`localeCompare` は Workers と Node で結果が変わりうる）。
- **一覧の絞り込み・並べ替え・ページングはメモリで行う**（`queryProducts`、キャッシュ済みの全件から）。小規模ショップ前提で、SQL に条件を足すより isolate キャッシュが効く。数千件規模になったら PostgREST 側に寄せる。
- **バックアップ復元のタグは別 RPC `restore_product_tags`**（slug で突き合わせ）。151 行の `restore_shop_data` を複製して書き換えるより、差分の小さい関数を足すほうが前方専用マイグレーションとして安全。
- **0007 を適用する前でも商品保存を壊さない**: 管理画面は tags 列が無い（PGRST204）とき、タグが空ならタグ抜きで保存し直し、タグありなら「アップデートを適用して」と案内する。`main` への push がそのまま本番になるため、デプロイとマイグレーション適用の間に穴を開けない。（2026-10-17: v0.1.0 の土台に入ったのでこの逃げ道は消した。以後は `migrated()` で判定する）
- **境界を「レジ」から「判定」へ広げた（人間が決定）**: 画面はカート・配送先・最終確認まで連携側が自由に作ってよい。Banto はカートの中身・価格・在庫・送料・合計・注文確定の**判定**を手放さない。カート API・チェックアウト API・購入リンクは docs/headless.md。計算は `src/commerce/checkout.ts` に一本化し、同梱テーマのレジも同じ道を通る。
  - カートはサーバーに状態を持たない署名付きトークン（カート Cookie と同じ形式）。DB に匿名の書き込みをさせない（スパム行と掃除の Cron が要らない）。Cookie ではないので別ドメインの WordPress からも動き（Safari 等のサードパーティ Cookie 制限に掛からない）、CSRF も成立しない → 公開 API は CORS `*`。
  - 在庫はカートに入れた時点では押さえない。確保は従来どおり確定時（§6）。
- **特商法の最終確認画面を追加した**（v0.1 のレジに無かった）: 配送先入力 → **最終確認** → 在庫予約と決済ページ。数量・単価・送料・支払総額・支払方法と時期・引渡時期・取消し / 返品の条件・お届け先・法務リンクを表示する。引渡時期と取消し条件はショップ設定 `settings.checkout_terms`（未設定なら法務ページへ案内し、管理画面で警告）。公開のブロックにはしていない（既存ショップを止めないため。要否は人間が判断）。
  - 確認画面の内容は署名付きの **quote**（品目・単価・送料・合計・配送先、1 時間有効）に固め、確定時に価格・送料・在庫を引き直して**1 円でも違えば確定せず確認し直させる**。見せていない金額で申込みが成立しない。
  - チェックアウト API（段階 C）では連携側の画面が最終確認画面になる。法的義務は常に運営者（販売業者）にあり、C では表示の担保が連携側の実装に移ることを docs/headless.md に明記した。文言の適法性は専門家の確認が未実施。
- **API の決済後の戻り先は許可リスト**（`settings.headless.return_origins`、https のオリジンのみ）。それ以外は Banto の完了画面に戻す（オープンリダイレクト対策）。
- **Banto の立ち位置は「ヘッドレス・コマースのバックエンド + 既定のストアフロント 1 本」**。表示（一覧・詳細・LP・SNS）は連携側が自由に作り、カートから先（在庫予約・送料・配送先・特商法・決済・注文確定・注文照会・会員）は Banto が手放さない。同梱テーマはレジを含む参照実装なので捨てない。連携側の作り方は docs/headless.md。
- **CRM を顧客マスタにして Banto から個人情報を抜く構成は採らない**。CRM は hooks の送信先（外部プラグイン）、個人情報は `orders:pii` スコープ経由のまま。小規模事業者に外部 SaaS の契約を前提にさせない。
- **取り置きは「店頭受け取り（決済済み、配送方法の一種）」だけをやる**。決済なしで在庫を日単位で押さえる形は、注文が Webhook でしか確定しない設計と衝突するので、やるなら単独の設計書から。
- **LINE LIFF 購入・ギフト・買い増し・請求書払いはコアに入れない**（外部プラグイン案件か、個別設計）。理由: LINE LIFF の購入は LINE Login・LIFF・Messaging API でひとつの製品の規模で、hooks と API だけで外から作れる。ギフト・買い増しは在庫の不変条件か「カード情報を扱わない」に触れる。請求書払いは「未入金の注文」という状態を足す話で小さくない。

## 2026-10-15

- **マイグレーションは Supabase Management API 経由を既定にした**（`src/db/migrate-api.ts`）。Workers から Supabase の pooler に TLS で直接つなぐと、ハンドシェイク直後に切られる（workerd #2712）。接続文字列の経路（`src/db/migrate.ts`）は Node 実行とローカル Supabase 用に残す。Hyperdrive は §1-2 で禁止。
- **運営者の初回作成は GoTrue Admin API で確認済みユーザーを作る**。signup だと確認メールのリンク先が Supabase の Site URL（既定 localhost:3000）になり、非技術者が詰まる。会員の signup は従来どおり（`redirect_to` を付ける）。
- **`wrangler.jsonc` に `vars` を書かない、`keep_vars: true`**。空の `vars` を書いていると、ビルドのたびに wrangler が画面で入れた値を空で上書きする。必須の 3 値は `.dev.vars.example` に `REPLACE_ME` 入りで列挙し、Deploy ボタンの画面で聞かせる。`REPLACE_ME` と空文字は ConfigAdapter が「未設定」として扱う。
- **wrangler.toml → wrangler.jsonc**。Deploy ボタンで動作報告のある構成がすべて jsonc だったため。
- **Checkout の `expires_at` は 35 分、在庫予約の TTL はその 5 分後**。Stripe の下限はちょうど 30 分で、通信の遅れで弾かれる。
- **Cron の経路で `fetch` は必ずラッパー関数にして渡す**。Workers では素の `fetch` をオブジェクトのプロパティ経由で呼ぶと `Illegal invocation`。
- **決済プラグイン（Stripe / KOMOJU）は hooks のイベントを購読しない**。受信処理が無いので、購読すると配信が失敗し続ける。設定画面からイベント欄を消し、既に積まれた配信は 204 で完了扱い。
- **ロケールと時間帯はデプロイ単位**（`BANTO_LOCALE` / `BANTO_TIMEZONE`）。リクエストごとの切り替えは isolate 内で競合するので持たない。売上集計の日別区切りだけは SQL 側で Asia/Tokyo 固定（海外運用が要るなら引数化する）。
- **Secret の形を管理画面で検査する**（`secretFormats`）。`sk_` と `whsec_` の取り違えが実際に起きた。
- **組織（Organization）の Stripe キーは `STRIPE_CONTEXT`（acct_…）で対応**。推奨はアカウント内で発行したキー。

## 2026-10-14

- **画像の縮小とサムネイルはブラウザ側**（canvas → WebP、1600px / 400px）。Cloudflare Images は固有機能、wasm は Workers Free の CPU 10ms に抵触。AI の URL 取り込みはサムネイル無し（テーマは本画像で代用）。
- **画像配信は R2 カスタムドメイン + `MEDIA_BASE_URL` を推奨**。Worker を通さないので無料枠の持ちが良い。既定（Worker 配信）でも動く。
- **バックアップは JSON 書き出し + 空ショップへの復元**（`restore_shop_data`、id 振り直し）。会員は同じ Supabase プロジェクトのときだけ戻る。
- **Cron の生存は `banto_heartbeats` + `/health` の `cron`**。全ジョブの最後に書くので、途中で落ちても stale になる。
- **英語 UI は `en.ts` にフル翻訳、キーの一致をテストで検査**。
- **外部プラグインの実例は本体のコードを読み込まない**（docs/hooks.md の契約だけで動く）。本体側のテストが署名の互換を検査。

## それ以前（v0.1 の骨格）

- Secret の受け渡しはコピー方式（運営者が Cloudflare の画面で貼る）。ウィザードは不足を検出して案内するだけ。
- Stripe は API キー方式が既定、Connect は上級設定。注文確定は Webhook のみ。
- 在庫の減算は Postgres の RPC だけ。予約 → 確定 → 解放。
- hooks の署名シークレットは DB に置かず導出。ペイロードに個人情報を載せない。
- AI 用トークンは `api_*` RPC だけを呼び、権限判定は SQL 側。
